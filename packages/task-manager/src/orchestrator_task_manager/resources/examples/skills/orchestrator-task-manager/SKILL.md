# Работа с Task Manager Service

Task Manager Service — источник истины о задачах. Его Python-пакет `orchestrator_task_manager` устанавливается отдельно от ядра Orchestrator. Уточни корень целевого проекта; передавай его явно через `--project` или в `TaskManagerService(Path(...))`. Не путай его с каталогом установленного пакета. База находится в `<проект>/.orchestrator/state/tasks.sqlite3` и не является интерфейсом для прямого редактирования.

## Обычная работа

- Для внешнего агента используй MCP stdio как основной интерфейс: клиент запускает `orchestrator-task-manager-mcp --project <проект>` одним отдельным процессом на каждый проект. Код пакета общий, `project_root` фиксирован при запуске, а база остаётся в `<проект>/.orchestrator/state/tasks.sqlite3`. Не пытайся переключить корень через аргумент инструмента.
- Для Python-оркестратора, работающего в том же процессе, вызывай `TaskManagerService(Path(<проект>))` напрямую. MCP и запуск CLI на каждую операцию в этом сценарии избыточны. CLI используй как резервный интерфейс, средство диагностики и ручной fallback.
- При MCP-сеансе сначала выполни стандартный `initialize`, дождись ответа, затем `notifications/initialized`, после чего получи каталог через `tools/list`. Вызывай только структурированные `tools/call`; аргументы строго соответствуют опубликованному `inputSchema`. Успешный `structuredContent` всегда объект: списки/строки находятся в `value`, объектные результаты — на верхнем уровне; предметные ошибки находятся в `error` с `isError: true`.
- Если MCP недоступен, CLI начинается с `orchestrator-tasks --project <проект> summary` или `list`, затем `show <ID>` и при необходимости `history <ID>`. По умолчанию архив скрыт; `--include-archived` показывает его. Используй JSON для обработки агентом; `--format table` — компактное чтение list/show/summary человеком. `api` показывает фактические сигнатуры Python, `<команда> --help` — обязательные флаги, `resources` — пути к документации без создания базы.
- Перед созданием задачи возьми название, исходный запрос, цель и критерии приёмки из запроса пользователя или согласованных материалов. Не выдавай предполагаемые критерии за утверждённые пользователем.
- Для изменений через MCP используй профильные инструменты полного lifecycle: `task_start_preparation`, `task_refine_definition`, `task_attach_artifact`, `task_attach_execution_package`, `task_mark_ready`, `task_claim`, `task_renew_claim`, `task_release_claim`, `task_recover_expired_claim`, `task_link_workflow_run`, `task_add_blocker`, `task_resolve_blocker`, `task_record_user_decision`, `task_transition_status`, `task_mark_awaiting_acceptance`, `task_complete`, `task_accept`, `task_cancel` и `task_archive`. Их guards совпадают с публичным сервисом.
- Каждая MCP-мутация после создания задачи требует актуальную `expected_version`; сначала прочитай карточку через `task_get`. В Python сначала прочитай `version` и передай `expected_version`. Для поддерживающих методов используй `operation_id`, сохраняя исходные параметры, включая первоначальную версию. При конфликте заново прочитай карточку и оцени изменение; слепого повтора нет.
- В CLI те же операции доступны как start/refine/artifact/execution-package/ready, claim/renew/release/recover, run-link, blocker-add/blocker-resolve, decision/transition, awaiting-acceptance/complete/accept/cancel. CLI сам читает версию, а для намерения, привязанного к прочитанной карточке, передай `--expected-version`.
- `--operation-id` доступен только поддерживающим его командам (см. --help). Для повтора сохраняй исходные параметры, включая первоначальную --expected-version; версия входит в отпечаток. create требует одинаковых данных без версии. После неопределённого результата команды без operation-id проверь карточку и историю прежде нового вызова. Для происхождения события поддерживаемые методы принимают event_context.
- Не назначай статус записью в JSON или SQLite. `ready` требует каноническую карточку задачи, актуальный `plan.md` по SHA-256, одобренный review и Execution Package; отдельная specification не требуется. `active` достигается только через claim. Не регистрируй фиктивные артефакты, запуски, решения пользователя или приёмку ради обхода защитных условий. Состояние графового запуска принадлежит Graph Runtime, здесь хранятся лишь ссылки.
- После мутации проверь обновлённую карточку и историю; через MCP используй `task_get`, `task_history` и `task_health_check`, через CLI — `show`, `history` и `validate`. Диагностика сообщает о проблемах, но не чинит их. При блокировке верни пользователю код и смысл ошибки без прямой правки базы.
- `accept` атомарно регистрирует уже полученную явную приёмку пользователя и завершает задачу; обязательны --candidate-revision и --completion-decision-ref. Разрешение реализовать работу не означает приёмку ещё не показанного результата. Архивация обратима; purge разрешён только архивной completed/cancelled после трёх календарных месяцев retention. Перед restore останови другие процессы и мутации Task Manager; на Windows открытая БД препятствует замене. Панель остаётся только локальной и только для чтения.

Для типовых команд читай [инструкцию](../../../docs/usage.md); перед защищёнными переходами и при ошибках читай [контракт](../../../docs/contract.md). Эти файлы включены в дистрибутив Task Manager Service.
