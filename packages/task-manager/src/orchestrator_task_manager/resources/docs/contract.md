# Task Manager Service: действующий контракт

**Статус:** действующий реализованный контракт, актуализирован 2026-09-16. Этот документ поставляется внутри пакета `orchestrator-task-manager` и не требует документов ядра Orchestrator.

## Ответственность и данные

`TaskManagerService` — детерминированный владелец состояния задачи. Он не анализирует требования, не выбирает узел графа, не выполняет код и не редактирует проект. Состояние запуска принадлежит внешнему Graph Runtime; задача содержит лишь `run_ref`. Внешний трекер может быть проекцией, но не источником истины.

Каноническое состояние хранится в `<project_root>/.orchestrator/state/tasks.sqlite3`. Эта база локальна и не должна попадать в Git. Создание проекта или онбординг для работы сервиса не обязательны: нужен существующий каталог `project_root`. План реализации размещается в `.orchestrator/tasks/TASK-xxxx/plan.md`. Сервис не создаёт этот файл, но при привязке и переходе в `ready` проверяет его путь и SHA-256. Старые `specification.md` могут оставаться в исторических карточках, но не являются обязательным артефактом.

SQLite хранит снимки в `tasks`, события в `events`, операции идемпотентности в `operations`, tombstone удалённых задач в `purged_tasks` и счётчик ID в `meta`; текущая версия схемы — `PRAGMA user_version=5`. События также содержат nullable-метаданные `actor_ref`, `source`, `correlation_id`, `run_ref`. Схема создаётся через упорядоченный реестр миграций; будущие версии добавляются отдельными переходами, а неподдерживаемая версия отклоняется до записи. ID имеет вид `TASK-0001`, версия задачи начинается с 1. Каждая мутация требует `expected_version` и в одной транзакции `BEGIN IMMEDIATE` обновляет снимок и добавляет одно событие. Необязательный `operation_id` возвращает сохранённый результат повторной операции без нового события; другой отпечаток с тем же ID даёт `operation_conflict`. При конфликте версии возвращается `TaskError(code="task_version_conflict", details={"expected": ..., "actual": ...})`; автоматического слияния нет. Исходный запрос в снимке не изменяется. Прямые SQL-записи не входят в публичный API.

Снимок содержит название, тип, исходный запрос, цель, критерии приёмки, ограничения, версию определения, статус, ссылки на артефакты и запуски, lease, блокеры, решения пользователя, внешние ссылки и временные метки. Поддерживаемые типы: `implementation`, `analysis`, `investigation`, `incident`, `exploration`. История чата и содержимое документов в снимок не копируются.

## Статусы и защитные условия

Основной путь: `created → preparing → ready → active → awaiting_acceptance → completed`. Дополнительные статусы: `awaiting_input`, `blocked`, `cancelled`; `completed` и `cancelled` конечны. Подготовка начинается с `run_ref`; перед `ready` активная ссылка на запуск должна быть закрыта. Для `ready` нужны карточка задачи, одобренный `plan`, `plan_review` и `execution_package`, привязанные к одной версии плана, подготовленная ревизия источника и отсутствие открытых блокирующих факторов. Изменение определения или плана после `ready` аннулирует пакет и возвращает задачу к подготовке.

`ready → active` возможен только через атомарный `claim_task` с lease. Продление, освобождение и восстановление истёкшего claim сохраняются в истории. При активной ссылке на запуск автоматическое восстановление claim запрещено. Состояния ожидания пользователя и блокировки не снимаются простым освобождением claim; для возобновления нужны решение или разрешение блокера и повторная проверка готовности.

Архивация доступна только для `completed` и `cancelled`, не меняет их status и скрывает задачу из обычного списка. `unarchive_task` обратимо снимает архивный признак. `purge_task` физически удаляет snapshot и события только для архивированной задачи со статусом `completed` или `cancelled` после трёх календарных месяцев с terminal-события; операция сохраняет минимальный tombstone и не освобождает ID для повторного использования.

Переход к `awaiting_acceptance` требует артефакт `readiness` с `metadata.status="ready"`, `acceptance_package` и закрытый запуск. Завершение по умолчанию требует решение пользователя `acceptance=approved` для текущей `candidate_revision` и отсутствие открытых блокеров. Сервис проверяет факт регистрации свидетельств, но не делает вывод о качестве реализации. Отключение обязательной пользовательской приёмки доступно только явным параметром `acceptance_required=False` при создании сервиса.

`accept_task` атомарно регистрирует явную пользовательскую приёмку и завершает задачу. Обязательны `candidate_revision` и `completion_decision_ref`; приёмка допустима только в `awaiting_acceptance` и для текущей ревизии `readiness`. В одной транзакции добавляются решение в карточку, completion-артефакт и одно событие `task_completed` с `payload.user_decision`. При ошибке guard решение также не сохраняется. Команда не заменяет разрешение пользователя; агент вызывает её только после явной приёмки соответствующего результата. Раздельные `record_user_decision` и `complete_task` сохраняются для прежних клиентов.

## Публичный API

Реализация разделена на модули по [внутренней архитектуре](architecture.md). Это не меняет контракт: классы доступны из пакета и прежнего `orchestrator_task_manager.task_manager`, схема SQLite остаётся версии 5.

Импорт: `from orchestrator_task_manager import TaskManagerService, TaskError`. Конструктор принимает `Path` корня проекта и необязательные `clock`, `acceptance_required`. Возвращаемые задачи и события — словари Python; их изменяемость в памяти не заменяет вызов сервисного метода.

| Группа | Методы |
| --- | --- |
| Создание и чтение | `create_task`, `get_task`, `list_tasks`, `summary`, `get_history`, `get_document`, `get_claim`, `list_executable_tasks`, `health_check` |
| Хранение | `archive_task`, `unarchive_task`, `purge_task` |
| Перенос состояния | `export_state`, `backup`, `restore` |
| Подготовка | `start_preparation`, `refine_task_definition`, `update_metadata`, `attach_artifact`, `attach_execution_package`, `mark_ready` |
| Исполнение и пауза | `claim_task`, `renew_claim`, `release_claim`, `recover_expired_claim`, `link_workflow_run`, `add_blocker`, `resolve_blocker`, `transition_status` |
| Приёмка и интеграции | `record_user_decision`, `mark_awaiting_acceptance`, `complete_task`, `accept_task`, `cancel_task`, `register_external_link` |

`create_task` требует `title`, `task_type`, `objective`, `original_request`, непустой список `acceptance_criteria`; ключевые мутации принимают `operation_id` и `event_context`. Для остальных мутаций первым аргументам после `self` обычно соответствуют `task_id` и текущая `expected_version`; дополнительные именованные параметры смотрите в сигнатуре метода. Роли артефактов ограничены набором `ARTIFACT_ROLES` в `contracts.py` (переэкспорт сохранён в `task_manager.py`); для `plan` нужен путь внутри каталога задачи и SHA-256. `get_document` сохраняет чтение `plan` и legacy `specification` с повторной проверкой хеша. `list_tasks` по умолчанию скрывает архив, а `include_archived=True` возвращает его; фильтры и cursor-пагинация сохраняются. `health_check` выполняет диагностику, но ничего не исправляет. `export_state` включает архивные задачи и tombstone удалённых, `backup` — консистентную копию SQLite, а `restore` проверяет копию до атомарной замены и сохраняет `.pre-restore`.

Исключение `TaskError` содержит `code`, сообщение и `details`; `as_dict()` готовит машинный ответ. Основные коды: `validation_failed`, `task_not_found`, `task_purged`, `invalid_transition`, `guard_failed`, `retention_not_elapsed`, `task_not_ready`, `task_version_conflict`, `operation_conflict`, `claim_conflict`, `claim_expired`, `repository_failure`. После конфликта версии заново прочитайте задачу и решите, применимо ли исходное намерение; не повторяйте мутацию автоматически.

Часы нормализуются в UTC; naive `datetime` явно трактуется как UTC, aware-значение переводится в UTC. Это одинаково действует для временных меток, lease и retention. Иной тип результата `clock` отклоняется как `validation_failed`. Пропущенные обязательные аргументы и неправильная сигнатура Python дают стандартный `TypeError`; ошибки переданных предметных значений дают `TaskError`.

Архив фильтруется структурно в SQL до применения LIMIT. JSON1 используется при наличии; на SQLite без JSON1 регистрируется совместимая функция без внешней зависимости. `summary` принимает те же status/type/query/archive-фильтры, что и список, и выполняет SQL-агрегацию. `total`, `by_status`, `by_type` относятся к выбранным карточкам; архив по умолчанию исключён, tombstone никогда не входит в total. `archived_total` и `purged_total` — глобальные счётчики проекта, независимо от фильтров. Список и summary не проверяют качество работы и готовность артефактов.

SHA-256 документов считается потоково с блоком до 64 KiB. `get_document` читает один набор байтов, проверяет его хеш и декодирует UTF-8 с прежней нормализацией переводов строк. Метод возвращает полный текст, поэтому его память зависит от размера документа. Недоступный файл при привязке даёт `validation_failed`, при ready-guard — `guard_failed`; ошибки чтения между проверкой пути и чтением документа также дают `guard_failed`. Физически отсутствующий файл на этапе проверки пути остаётся `validation_failed`. Диагностика сообщает нарушения guard, не изменяя карточки.

`export_state`, `summary` и `health_check` читают единый транзакционный снимок SQLite. Временные файлы export/backup/restore имеют уникальные имена; чужие файлы с суффиксом `.tmp` не удаляются. Ошибки файлового ввода-вывода операций переноса дают `repository_failure`, не заменяя прежний целевой файл при неуспешной записи. Restore проверяет integrity, структуру таблиц и внешние ключи, мигрирует временную копию до текущей схемы, создаёт `.pre-restore` через SQLite backup и только затем заменяет рабочую БД. Исходный backup не мигрируется и не перезаписывается; при восстановлении из самого `.pre-restore` новая safety copy получает уникальный суффикс. Restore требует остановить другие процессы и мутации Task Manager; атомарная замена файла не является протоколом координации работающих клиентов. На Windows открытая БД может препятствовать замене. Деталь `safety_copy` при ошибке указывает только копию, созданную текущей попыткой.

## Пределы среза

Пакет не включает Task Creator, Artifact Repository, Graph Runtime, Executor Loop и синхронизацию с внешним трекером. CLI и локальный MCP stdio-адаптер предоставляют чтение, подготовку, защищённые мутации исполнения, приёмку и перенос состояния через публичный сервисный API. MCP запускается с одним фиксированным `project_root`; его файловые аргументы export/backup/restore не могут выйти за этот корень. Без `--expected-version` CLI читает текущую версию перед мутацией; MCP требует её для мутаций явно. С флагом CLI использует указанную версию. Конфликт не повторяется автоматически. Для повтора с `operation_id` нужно сохранить первоначальные параметры, включая expected_version: версия входит в отпечаток. После purge тот же вызов с исходной версией и operation_id возвращает сохранённый результат даже при удалённой карточке.

Команда `orchestrator-task-manager-mcp --project <root>` запускает JSON-RPC stdio-сервер без внешних зависимостей. Клиент сначала выполняет `initialize`, получает ответ, затем отправляет `notifications/initialized`; только после этого доступны `tools/list` и `tools/call`. Входы строго проверяются по опубликованным JSON Schema: типы, enum, обязательные и неизвестные поля не приводятся молча и возвращают `validation_failed`. Каждый ответ `tools/call` имеет объект `structuredContent`: объектный результат сохраняется как есть, список или строка помещается в поле `value`, ошибка — в поле `error` с `isError: true`. Уведомления без `id` не вызывают мутаций и не получают ответ. MCP не добавляет собственное состояние и не пишет SQLite напрямую.

JSON — формат по умолчанию; обёртка `ok/result` и коды выхода 0 (успех), 1 (validate обнаружил нарушения), 2 (ошибка) сохранены. Ошибки разбора CLI также возвращаются как JSON на stderr. `--format table` применяется к list/show/summary, остальные результаты остаются JSON. `--project` и `--format` допустимы до и после команды; последнее указанное значение побеждает. Команды `api` и `resources` не открывают и не создают проектное состояние. Практические команды и пример Python API — в [инструкции](usage.md).
