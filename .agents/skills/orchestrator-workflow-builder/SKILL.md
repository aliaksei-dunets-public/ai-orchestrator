# Конструктор процессов Orchestrator

Помогай пользователю проработать процесс и превращай согласованные решения в проверяемое определение. Основной интерфейс — беседа; пользователь также может редактировать TOML вручную.

## Контекст

Найди корень ядра с `orchestrator/workflow_builder.py` и `workflow-library`. Для внешнего проекта сначала прочитай `.orchestrator/project.json`: `core_path` указывает подключённое ядро. Не путай корень ядра с целевым проектом. Прочитай актуальные `docs/project-status.md` и `docs/architecture/workflow-builder.md` ядра. Для формата и рабочих команд используй `docs/guides/workflow-builder.md`; не придумывай API отсутствующих этапов.

В текущем v1 конструктор проверяет и компилирует определения, но не запускает LLM, инструменты, процесс задачи или фасады ready/claim. Модельные профили описывают намерение выбора. Генерация HTML показывает определение, а не выполнение. Изменение задачи требует отдельного Task Manager API/skill только если входит в поручение.

Если поручение включает исполнение, прочитай `docs/architecture/workflow-execution.md` и `docs/guides/workflow-execution.md`: отдельный WorkflowExecutor материализует bindings и вызывает только зарегистрированные host adapters. Проверь доступность точной модели/capability; не выдавай заполнители профилей или локальный fixture за вызов LLM. Fallback только явный. Для фасадов сохрани WorkflowSource в preparation/package/preflight и используй зарегистрированный role contract/handler; package/ready/knowledge guards не заменяются. При pending effect сначала сверяй результат, не повторяй physical invocation. Отдельная приёмка пользователя остаётся обязательной после показа кандидата.

## Проектирование и сборка

Из беседы установи цель, внешние входы/результаты, этапы, успешные и ошибочные маршруты, повторы, ожидания и ограничения побочных эффектов. Уточняй только отсутствующие существенные сведения; сохраняй уже согласованные решения.

Получай каталог через `python -m orchestrator.workflow_builder catalog --library <библиотека>`. Читай manifests выбранных блоков и их схемы контрактов. Предпочитай существующий блок при соответствии задаче. Новый экземпляр, новый атомарный узел и новый подграф — разные результаты; не создавай копию manifest ради изменения модели или параметра экземпляра.

При создании блока объяви фиксированные ID/версию, назначение, входы/выходы, обязательные порты каждого outcome, instruction/skill либо capability исполнителя, config schema и эффекты. Для собственного контракта создай JSON-файл в `contracts/` с поддерживаемым подмножеством схем. Библиотечные примеры Testing/Documentation — упрощённые определения, не полная реализация одноимённых архитектурных контрактов execution gates.

Собери TOML с `ref`, явными bindings, переходами и exits. В подграфе `exit:outcome` возвращает управление caller; не указывай внутренние узлы родителя. Глобальные terminal_states задаёт корневое определение. Wait outcomes `needs_input`/`blocked` остаются на текущем экземпляре; повтор имеет конечный runtime budget.

Для целевого проекта используй явный overlay `patch`/`replace`; внутренние экземпляры адресуются полным ID. Совместимость replacement проверяет tooling. Изменение внешнего интерфейса требует изменения caller/версии контракта, а не обхода validator.

## Проверка и представление

Выполни `validate`, затем `export --json ... --html ...` из корня ядра с абсолютными путями определения, overlay и выходных файлов целевого проекта. Все используемые библиотеки передавай через повторяемый `--library`. Подробные команды — в guide; модель, capability и инструкция в manifest не являются разрешением на их фактическое исполнение.

Если проверка не прошла, исправь причину или явно сообщи о недостающем контракте; не выдавай непроверенный граф за готовый. После экспортирования открой локальную HTML-схему и предложи пользователю изучить узлы и маршруты. Передай ссылки на TOML, HTML, digest и результаты проверок. По уточнениям пользователя меняй определение и повторно генерируй представление из того же проверенного источника.

Для договорённостей по модели, проектной политике и дальнейшей интеграции читай [архитектурные основания](references/architecture.md).
