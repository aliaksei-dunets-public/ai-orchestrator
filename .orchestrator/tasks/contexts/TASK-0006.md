# TASK-0006 — Post-task finalization enforcement

## Исходный запрос

Создать задачу, устраняющую разрыв между инструкциями оркестратора и фактическим
runtime: после выполнения задачи должны быть проверены документация, граф знаний
и память, а завершение не должно обходить эти действия.

## Цель

Сделать документационную, knowledge и memory финализацию проверяемой частью
execution workflow и запретить переход новой задачи в `done` без связанного с
текущим контекстом успешного finalization evidence.

## Проблема или потребность

Спецификации и skills задают последовательность documentation → memory and
knowledge → commit → done, а `workflows/backlog-loop.yaml` объявляет post-task
session report и memory candidates. При этом runtime `run_backlog()` переходит
напрямую от execution к commit/complete, а `TaskManager.complete()` проверяет
только допустимость перехода, workspace/commit evidence и удаляет checkpoint.

## Текущее поведение

Documentation Manager, Knowledge Curator, Memory Manager и Session Reporter
существуют как отдельные навыки и API. Их вызов не является обязательным
runtime gate: direct CLI/API completion может завершить задачу без documentation
disposition, knowledge proposal и memory proposal/promotion evidence, а
декларативные `session-report` и `propose-memory-candidates` не вызываются
Backlog Loop.

## Ожидаемое поведение

После implementation/review/security и до commit оркестратор запускает единый
Task Finalization Coordinator. Он требует update или explicit N/A для
затронутой документации, валидный Knowledge Curator proposal, а также
policy-compliant memory proposals/promotions. Успешный coordinator выдаёт
receipt, связанный с task/context/checkpoint/changed paths; без него Task Manager
не завершает задачу. После остановки backlog Session Reporter формирует отчёт и
approval-gated session memory proposals, не являясь условием статуса отдельной
задачи.

## Анализ

Проверенные runtime paths: `orchestrator/backlog.py` вызывает
execute → commit → complete и не реализует `post_task`; `orchestrator/task_manager.py`
не принимает finalization evidence; `orchestrator/session_report.py` только
предоставляет функции формирования отчёта и candidates. При этом
`orchestrator.documentation`, `orchestrator.knowledge_bootstrap` и
`orchestrator.memory` уже содержат большую часть необходимых validation,
provenance и approval primitives, поэтому gap следует закрыть coordinator-слоем,
а не дублированием подсистем.

Свежий bounded context pack получен до анализа. Memory и Knowledge stores не
вернули релевантных записей, поэтому дополнительных проектных решений нет.

## Выбранный подход

Добавить `TaskFinalizationCoordinator` и versioned `FinalizationReceipt`.
Coordinator детерминированно связывает результаты документации, knowledge и
memory с текущим Task Context, execution checkpoint и changed paths. Task
Manager валидирует структуру и freshness receipt, не подменяя semantic review.
Backlog и CLI обязаны запускать coordinator до commit/complete. Session Report
остаётся отдельным post-loop шагом согласно действующей спецификации.

## Рассмотренные альтернативы

- Оставить финализацию только инструкцией для агента — отклонено, поскольку это
  сохраняет существующий runtime bypass.
- Выполнять обновления внутри `TaskManager.complete()` — отклонено: Task Manager
  не должен владеть semantic documentation/knowledge/memory logic или начинать
  tracked writes после commit.
- Всегда автоматически продвигать memory candidates — отклонено из-за
  source-authority и approval policy.
- Требовать непустой graph diff для каждой задачи — отклонено: пустой proposal
  является корректным доказательством отсутствия graph-relevant изменений.
- Сделать Session Report условием `done` — отклонено как противоречащее
  спецификации, где отчёт формируется после остановки execution/backlog loop.

## Объём задачи

### Входит в scope

- finalization contract, receipt schema, freshness/digest binding и recovery;
- documentation impact/update-or-N/A/link-validation gate;
- empty/non-empty Knowledge Curator proposal validation and atomic application;
- memory proposal, source-authority, promotion and approval dispositions;
- Task Manager, CLI, serial and isolated-parallel backlog enforcement;
- post-loop session reporting and session memory proposals;
- workflow, Health, canonical skill, specification, ADR, migration and guide
  updates;
- unit, contract, scenario, Git sandbox, security and release acceptance tests.

### Не входит в scope

- генерация качественного semantic content без участия agent skills;
- ослабление approval для instructions или non-authoritative memory;
- обязательный непустой graph/memory diff для каждой задачи;
- превращение Session Report в per-task completion gate;
- distributed transactions, remote workers, database backend или UI;
- реализация `TASK-0004` English-first migration внутри этой задачи.

## Затрагиваемые компоненты

- `orchestrator/finalization.py`, `documentation.py`, `knowledge_bootstrap.py`,
  `memory.py`, `session_report.py`, `execution.py`, `backlog.py`,
  `task_manager.py`, `task_cli.py`, `cli.py`, `health.py`;
- task finalization and registry schemas, documentation map;
- task execution/backlog workflows and canonical system skills;
- Task Layer/orchestrator specifications, component contracts, ADR, migration,
  memory/knowledge guide and release acceptance.

## Критерии приёмки

- AC1: New completion transitions reject missing, malformed, stale, forged or
  unsuccessful receipts bound to task/context/checkpoint/changed paths.
- AC2: Every impacted canonical document is updated or has explicit N/A evidence,
  and broken local links block finalization.
- AC3: Empty knowledge proposal is a valid no-op; non-empty proposals apply
  atomically with provenance, ontology, secret and conflict checks.
- AC4: Memory candidates are idempotent and follow source-authority/approval
  policy; instructions and session sources cannot bypass approval.
- AC5: Serial and isolated-parallel flows run finalization before commit and
  complete, preserving stop/resume/worktree behavior.
- AC6: Session report and session memory proposals run once after backlog stop
  without changing completed task status.
- AC7: Historical done records, list/show, cancellation and recovery remain
  compatible.
- AC8: CLI, workflows, schemas, skills, Health and canonical documentation agree.
- AC9: Focused/full tests, strict Health, audit and security review pass.

## Ограничения

- Python 3.11+ standard library for runtime paths.
- Canonical source ownership, project-relative provenance and append-only memory
  lifecycle remain unchanged.
- Task Manager performs structural validation only; semantic gates remain owned
  by the coordinator skills.
- Operational receipts/proposals/checkpoints/indexes remain ignored.
- Existing user changes and `TASK-0004` artifacts must be preserved.
- `TASK-0006` must not execute concurrently with `TASK-0004` because both touch
  canonical specifications/workflows.

## Риски

- Forged receipt bypass; mitigation: schema plus context/checkpoint/changed-path
  digest binding and negative API/CLI tests.
- Partial canonical writes; mitigation: prepare-all/validate-all before atomic
  apply and append-only recovery.
- Approval stalls unattended execution; mitigation: `waiting_user`, persistent
  proposal/checkpoint and idempotent resume.
- Retry duplicates; mitigation: stable proposal/content/source digests.
- Existing task compatibility; mitigation: require receipts only for new
  completion transitions and retain legacy read validation.
- Documentation conflict with TASK-0004; mitigation: serial dependency and
  freshness revalidation.

# Execution Record

## Итог выполнения

- Реализован `TaskFinalizationCoordinator` с versioned receipt, привязкой к
  Task Context revision/baseline, completed checkpoint и changed-paths digest.
- Documentation gate требует update либо explicit `not_applicable` для каждого
  impacted canonical document и валидирует локальные ссылки.
- Knowledge gate поддерживает валидный empty no-op и атомарное применение
  non-empty proposal с rebuild производного индекса.
- Memory gate создаёт идемпотентные proposals, автоматически продвигает только
  authoritative non-instruction candidates и сохраняет hash-bound approval
  policy для остальных источников.
- Task Manager, CLI, serial и isolated backlog требуют финализацию до commit и
  `done`; post-loop Session Reporter выполняется один раз и не меняет уже
  установленный task status.
- Канонические навыки, platform projections, workflows, schemas,
  specifications, ADR, migration, guide и release contract синхронизированы.

## Решение для памяти проекта

Завершение новой задачи требует актуальный finalization receipt, который
подтверждает documentation, knowledge и memory gates до commit и перехода в
`done`.

## Остаточные ограничения

- Task Manager проверяет структурную целостность и freshness receipt; качество
  semantic content остаётся ответственностью coordinator skills и review gates.
- Между knowledge JSONL и append-only memory lifecycle нет распределённой
  транзакции; recovery выполняется идемпотентным повтором и
  disable/supersede-механизмами.
