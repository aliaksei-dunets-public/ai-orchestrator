# TASK-0002 — Full project memory and knowledge lifecycle

## Исходный запрос

Создать план реализации полного scope для Knowledge Graph и Project Memory в
Core и target project.

## Цель

Завершить переносимый, безопасный и проверяемый lifecycle памяти и графа:
target-owned canonical stores, policy-gated promotion, additive ontology,
bounded retrieval, onboarding, CLI, workflows, Health Check, migration и
acceptance evidence.

## Проблема или потребность

Фазы 17–18 предоставили минимальные Python primitives и схемы, но целевой
проект не получает stores, execution workflows не читают и не курируют знания,
а CLI и Health Check не покрывают lifecycle. В результате реализованный
контракт нельзя полноценно использовать между сессиями и проектами.

## Текущее поведение

`orchestrator.memory` умеет append/load, duplicate/stale/secret checks и
supersede. `orchestrator.knowledge` умеет добавлять nodes/edges и строить
минимальный deterministic index. Эти модули вызываются только тестами.
Onboarding создаёт config, Project Context, skill projection и Task state, но
не memory/knowledge layout.

## Ожидаемое поведение

Каждый target project владеет tracked canonical memory/knowledge data,
операционные proposals и derived indexes исключены из Git, promotion следует
source-authority/approval policy, retrieval детерминированно формирует bounded
context pack, а onboarding, task workflows, CLI, Health Check и migration
поддерживают lifecycle end-to-end.

## Анализ

Корневая причина — фазы 17–18 завершили минимальные acceptance criteria, но не
определили project storage ownership и integration boundary. Existing APIs
должны остаться совместимыми в 1.x, поэтому lifecycle добавляется как
project-root-aware слой с compatibility adapters, а не заменяет primitives.
Основные риски: загрязнение памяти, stale approval, secret leakage, graph как
второй source of truth, ontology drift и случайное исключение canonical data
из Git.

Evidence:

- `orchestrator/memory.py`;
- `orchestrator/knowledge.py`;
- `orchestrator/onboarding_workflow.py`;
- `orchestrator/health.py`;
- `workflows/task-creation-standard.yaml`;
- `workflows/task-execution.yaml`;
- `docs/specifications/orchestrator-specification-ru.md`;
- `docs/migrations/1.0.md`.

## Выбранный подход

Использовать target-owned tracked JSONL для canonical memory/graph и tracked
approval provenance. Proposals, indexes и migration backups являются
ignored operational/derived state. Promotion использует утверждённую
source-authority model; instruction всегда требует explicit approval.
Knowledge Graph использует immutable Core ontology и additive project
extensions. Retrieval выполняет bounded lexical selection и graph expansion
без embeddings или внешней БД. Подход явно утверждён пользователем
2026-07-28.

## Рассмотренные альтернативы

- Core-owned shared stores отклонены: смешивают состояние проектов и нарушают ADR-0001.
- Commit derived indexes отклонён: создаёт воспроизводимый шум и merge conflicts.
- Полностью ignored memory/knowledge отклонены: теряется командная переносимость и provenance.
- Approval каждой записи отклонён: создаёт избыточную интерактивность для уже утверждённых sources.
- Автоматическая запись всех observations отклонена: быстро загрязняет долговременную память.
- Embeddings/vector database отклонены: добавляют зависимости и недетерминированность без подтверждённой необходимости.

## Объём задачи

### Входит в scope

- project-owned storage layout и Git policy;
- schema contracts, Core ontology и additive project ontology;
- source authority, proposals, approvals, promotion, disable и supersede;
- complete graph validation and deterministic indexes;
- bounded deterministic retrieval and context packs;
- onboarding, migration, rollback and compatibility adapters;
- JSON-first CLI and task/backlog/audit workflow integration;
- Health Check, security gates, canonical skills and projections;
- specifications, deployment/migration guides, release 1.2 and acceptance evidence.

### Не входит в scope

- embeddings, vector databases and network synchronization;
- concurrent modifying writers and interprocess locks;
- cross-project shared memory;
- automatic instruction generation or promotion;
- web UI and arbitrary natural-language query service;
- unrelated Task Manager, telemetry or platform refactors.

## Затрагиваемые компоненты

- `orchestrator/memory.py`, `orchestrator/knowledge.py`;
- new source-authority, ontology, retrieval, CLI and migration modules;
- `orchestrator/onboarding_workflow.py`, `orchestrator/health.py`, security and audit;
- `config/schemas/`, Core defaults and ontology;
- task creation/execution/backlog workflows and registries;
- canonical system/bundled skills and generated projections;
- target `.orchestrator/` config, stores and Git policy;
- self-hosted memory/knowledge stores этого репозитория;
- specifications, ADR, guides, migration and release contracts;
- unit, contract, scenario, acceptance and multi-project tests.

## Критерии приёмки

- AC1: Onboarding создаёт или сохраняет tracked canonical stores и игнорирует только proposals, indexes и backups.
- AC2: Legacy schema-version-1 records и Python call sites читаются; migration preview/apply/rollback сохраняет content и provenance.
- AC3: Observation/lesson/decision без user approval продвигаются только из authoritative unchanged source.
- AC4: Instruction и non-authoritative proposal требуют approval, привязанного к proposal/source hashes.
- AC5: Disable/supersede append-only, сохраняют history и дают deterministic effective state без cycles/conflicts.
- AC6: Core ontology immutable, project ontology additive, unknown/conflicting terms rejected.
- AC7: Graph writes требуют безопасный existing provenance и effective endpoint nodes; silent overwrite запрещён.
- AC8: Complete graph indexes атомарно и byte-for-byte воспроизводятся из canonical stores.
- AC9: Retrieval исключает invalid/stale/disabled/superseded/secret records и соблюдает budgets.
- AC10: Каждый quick/standard/deep Task Creation и Task Execution route получает fresh context pack; empty или irrelevant stores дают valid no-op.
- AC11: Memory/knowledge/context CLI имеют JSON output, stable exit codes и не печатают traceback на invalid input.
- AC12: Health Check находит store, path, provenance, lifecycle, ontology, reference, index и Git-policy defects.
- AC13: Onboarding/promotion/retrieval/migration/reports не сохраняют secrets и не читают excluded trees.
- AC14: Skills, schemas, workflows, registries, docs, version/release contracts согласованы; focused/full tests и strict Health проходят.

## Ограничения

- Python 3.11+ и standard library для runtime paths.
- Platform-neutral Core; platform behavior остаётся в profiles/adapters.
- Existing 1.x public memory/knowledge APIs сохраняются compatibility adapters.
- Single modifying process; без interprocess locking.
- Canonical documents остаются source of truth, graph — navigation layer.
- Immutable security policies и explicit instruction approval нельзя ослабить project config.
- Generated projections изменяются только через canonical skill installer.

## Риски

- Migration может повредить JSONL; mitigation — preview hash, verified backup, record/digest comparison и rollback.
- Context pack может стать скрытым instruction channel; mitigation — schema, kind separation, explicit instruction approval и bounds.
- Project ontology может переопределить Core; mitigation — immutable IDs и conflict validation.
- Approval может устареть; mitigation — binding к proposal hash и source digest.
- Canonical stores могут попасть под ignore; mitigation — onboarding and Health Git-policy checks.
- Retrieval может разрастись; mitigation — deterministic scores, depth/count/character limits.
