# TASK-0007 — Serial execution branch policy analysis

## Исходный запрос

Создать отдельную задачу и провести анализ поведения до подготовки плана:
в serial режиме оркестратор не должен создавать отдельную task-ветку или
Git worktree.

## Цель

Подтвердить источник создания task-ветки, определить минимальный контракт,
который гарантирует работу serial задачи в текущей ветке, и подготовить
evidence-based implementation plan без изменения runtime до его утверждения.

## Проблема или потребность

TASK-0006 была выполнена в единственном основном workspace и в serial режиме,
но перед выполнением агент вручную переключился на новую ветку
`codex/task-0006-post-task-finalization`. Такой branch lifecycle не является
частью serial runtime и не имеет автоматической интеграции в main.

## Текущее поведение

`TaskManager.claim_next()` не создаёт assignment при `serial`; вызов
`WorktreeManager` находится только в ветке `isolated_parallel`. Workflow
объявляет serial workspace как `main`, но канонический Implementation Runner
не запрещает агенту создавать или переключать task-ветку вручную.

## Ожидаемое поведение

Для serial task workflow и агентские инструкции явно требуют использовать
текущую ветку и основной workspace, не создавая и не переключая task-ветку и
worktree. Ветки, integration и cleanup остаются только в explicit
`isolated_parallel` path.

## Анализ

Проверенные факты:

- `TaskManager._claim_next_locked()` вызывает `_assign_isolated()` только при
  `settings.mode == "isolated_parallel"`; serial record остаётся без
  assignment.
- `WorktreeManager.create()` формирует branch/worktree только для task с
  isolated assignment; `main_assignment()` branch не создаёт.
- `workflows/task-execution.yaml` уже задаёт `serial: main`, однако это не
  описывает запрет на агентские Git branch операции.
- Git reflog показывает ручной `checkout` из `main` в
  `codex/task-0006-post-task-finalization` до коммита TASK-0006; `git worktree
  list` содержит только основной workspace.
- Активная TASK-0004 занимает serial slot, поэтому эта задача создаётся в
  backlog и не запускается до её завершения.

## Выбранный подход

Сначала зафиксировать политику в declarative workflow, каноническом навыке
исполнения и contract tests. Не добавлять branch lifecycle в serial runtime:
runtime уже не создаёт ветки, а дополнительное registry/Git состояние не
нужно для предотвращения агентского manual branch switch.

## Рассмотренные альтернативы

- Добавить serial branch assignment в Task Registry — отклонено: это меняет
  совместимый serial contract и не отличает заранее существующую ветку от
  созданной агентом.
- Принудительно выполнять `git checkout main` перед serial task — отклонено:
  это может уничтожить корректный пользовательский branch workflow и меняет
  Git state вне scope Task Manager.
- Ограничиться устным соглашением — отклонено: оно не создаёт проверяемого
  контракта для будущих агентов.

## Объём задачи

### Входит в scope

- Анализ Task Manager, Worktree Manager, workflow и agent instructions.
- Формулировка минимального contract change и acceptance matrix.
- Подготовка отдельного implementation plan после evidence-анализа.

### Не входит в scope

- Выполнение implementation changes до утверждения плана.
- Изменение статуса, branch или незакоммиченных файлов TASK-0004.
- Автоматический merge существующей ветки TASK-0006.

## Затрагиваемые компоненты

- `orchestrator/task_manager.py` и `orchestrator/worktree_manager.py` как
  runtime evidence.
- `workflows/task-execution.yaml` и `workflows/backlog-loop.yaml`.
- `skills/bundled/implementation-runner/SKILL.md` и managed projections.
- Task Layer specification и workflow contract tests.

## Критерии приёмки

- Анализ отделяет подтверждённый runtime факт от агентского branch поведения.
- Выбранная граница изменений не добавляет branch/worktree lifecycle в serial
  runtime без необходимости.
- Для каждого будущего implementation criterion определён executable check.
- Implementation plan содержит точные файлы, порядок, documentation impact,
  rollback и тесты.

## Ограничения

- TASK-0004 остаётся единственной активной задачей и её user-owned изменения
  не редактируются.
- Serial сохраняет возможность работать в уже выбранной пользователем ветке.
- Worktree/branch lifecycle isolated_parallel остаётся без изменений.
- До implementation требуется отдельная плановая проверка.

## Риски

- Инструкции могут не контролировать внешний Git UI; mitigation: явно
  ограничить оркестратор и тестировать workflow/skill contract, а не пытаться
  переписать пользовательский Git policy.
- Неправильный runtime guard может запретить легитимную работу пользователя в
  feature branch; mitigation: не менять current branch и не требовать main.
- Пересечение с TASK-0004; mitigation: backlog-only registration и отсутствие
  файловых изменений её scope.

## План реализации

- Зафиксировать repository evidence и validation matrix для serial/isolated
  boundary.
- Подготовить и проверить отдельный implementation plan после анализа.
- Запустить implementation только после завершения TASK-0004 или явного
  последовательного назначения пользователем.

## Plan Review

Analysis-first scope ограничен evidence и планированием, не меняет runtime,
не пересекается с активной TASK-0004 и оставляет отдельный implementation
review перед изменением workflow/skills.

## Открытые вопросы

- Решения пользователя не требуются для анализа. Выбор implementation plan
  будет представлен после фиксации evidence.
