# TASK-0001 — Agent-led platform-neutral project onboarding

## Исходный запрос

Создать удобный onboarding workflow, который ведёт агент: пользователь
подключает AI Orchestrator как Git submodule или копию, указывает путь к
`project-onboarding` skill, отвечает только на необходимые вопросы, проверяет
единый preview и подтверждает применение с автоматическим rollback.

## Цель

Реализовать зарегистрированный platform-neutral onboarding workflow,
детерминированные agent-invoked scripts и постоянную project integration без
копирования in-place core.

## Проблема или потребность

Существующий onboarding создаёт Project Context, но не координирует
interaction, profile resolution, preview, approval, instruction integration,
validation и rollback. Пользовательский гайд вынужден раскрывать внутренние
Python API.

## Текущее поведение

Пользователь вручную вызывает `orchestrator.release.install_artifact` и
`orchestrator.onboarding.onboard`, самостоятельно выбирает profiles и запускает
проверки. Отдельного `project-onboarding` workflow в registry нет.

## Ожидаемое поведение

Агент загружает указанный skill, вызывает JSON-producing scripts, задаёт вопросы
только при неоднозначности, показывает полный preview, получает approval,
применяет project-owned integration и автоматически откатывает изменения при
`ERROR` или `CRITICAL`.

## Анализ

Core уже содержит evidence collection, profile loaders, Health Check, atomic
Task Registry writes и skill projection installer. Новый coordinator может
переиспользовать эти контракты, оставив interaction платформенным адаптерам.
Profile metadata устраняет необходимость ветвления Core по названиям платформ.

## Выбранный подход

Использовать in-place core и зарегистрированный declarative workflow.
Реализовать platform-neutral state machine и agent script с операциями
`inspect`, `plan`, `apply`, `rollback`. Сохранять machine-readable project
config и короткий managed bootstrap block в platform instruction surface.
Привязать approval к plan hash и включить автоматический rollback.

## Рассмотренные альтернативы

- Интерактивный CLI wizard отклонён: диалог должен вести агент.
- Agent-only natural-language workflow без scripts отклонён: он не обеспечивает
  воспроизводимые hashes, atomic writes и rollback.
- Копирование core в `.orchestrator/core` отклонено: подключённый submodule или
  package является активным core.

## Объём задачи

### Входит в scope

- onboarding workflow и registry entry;
- schemas для config, interaction и session;
- profile-owned instruction/interaction metadata;
- inspect, plan, apply и rollback coordinator;
- canonical skill script и Codex projection;
- tests, specifications, component contracts и deployment guide.

### Не входит в scope

- интерактивный CLI wizard;
- загрузка releases из сети;
- глобальная установка Python или platform plugins;
- vendor UI automation;
- автоматическое исправление конфликтующих ownership markers;
- ослабление immutable policies.

## Затрагиваемые компоненты

- `orchestrator/onboarding_workflow.py`;
- `skills/project-onboarding/`;
- `workflows/` и `registries/workflows.json`;
- platform profiles and schemas;
- onboarding contract/scenario tests;
- canonical specifications and deployment guide.

## Ограничения

- Python 3.11+ и standard library.
- Core не содержит platform-name branches.
- До approval записи запрещены.
- Секреты и ignored trees не читаются и не сохраняются.
- Существующий пользовательский контент вне managed markers сохраняется.
- Любой stale preview блокирует apply.

## Риски

- Повреждение instruction-файла или `.gitignore`.
- Применение устаревшего approval.
- Сохранение credential-like ответа.
- Ложная переносимость абсолютного core path.
- Неполный rollback после validation failure.

## Критерии приёмки

- Agent может выполнить read-only inspect по пути к canonical skill.
- Неоднозначность возвращает структурированные варианты и рекомендацию.
- Preview полон и имеет детерминированный hash.
- Apply без approval или после изменения inputs ничего не записывает.
- Project config, context, instruction block и ignores создаются атомарно.
- User-owned content и manual blocks сохраняются.
- `ERROR`/`CRITICAL` запускает проверенный rollback.
- Второй onboarding не создаёт diff.
- Core остаётся platform-neutral.
- Registries, schemas, projections, specs и guide согласованы.
