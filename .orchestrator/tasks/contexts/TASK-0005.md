# TASK-0005 — Worktree-aware task execution modes

## Исходный запрос

Перейти от одного execution slot к выбору режима выполнения. В serial mode
сохранить последовательное поведение. В isolated parallel mode первая задача
должна выполняться в основном workspace, а вторая и последующие — в отдельных
Git worktrees и ветках.

## Цель

Дать пользователю безопасный выбор между текущим последовательным режимом и
ограниченным параллельным выполнением без совместного изменения одной рабочей
директории, сохранив первую задачу parallel-сессии в основном workspace.

## Проблема или потребность

Task Manager сейчас считает `in_progress` и `waiting_user` единым execution slot,
отклоняет второй `claim-next` кодом `ACTIVE_TASK_EXISTS` и рассчитан на одного
изменяющего writer. Backlog Loop также выполняет задачи последовательно, а
Task Context/Execution checkpoint не содержат workspace assignment.

## Текущее поведение

`claim-next` разрешает только одну активную задачу. Registry validation выдаёт
`MULTIPLE_ACTIVE_TASKS`, если активных задач больше одной. Все изменения проходят
через основной workspace; worktree lifecycle, registry lock и branch ownership в
проекте не реализованы.

## Ожидаемое поведение

В `serial` mode текущая модель полностью сохраняется. В `isolated_parallel` mode
run сначала назначает задачу с sequence 1 в main workspace; после её freshness,
clean-state и commit gates задачи sequence 2+ получают отдельные worktrees и
ветки от нового validated main `HEAD`. Registry writes блокируются, conflicts
останавливают интеграцию, а failed worktrees сохраняются для recovery.

## Анализ

Нормативная спецификация прямо фиксирует ограничение первой версии: один active
slot, один modifying process и отсутствие concurrent writers. Это ограничение
находится в `orchestrator/task_manager.py`, `backlog.py`, Task Layer
specification, backlog workflow и тестах. Без worktree isolation параллельная
реализация будет смешивать незакоммиченные изменения, поэтому изменение должно
включать не только счётчик активных задач, но и workspace/branch ownership,
cross-platform registry lock, recovery и integration gates.

Свежий bounded context pack был получен до анализа; memory и knowledge stores
пусты, поэтому дополнительных проектных решений из них нет.

## Выбранный подход

Добавить два режима: backward-compatible `serial` и `isolated_parallel` с явным
`run_id`, `max_workers`, assignment metadata и cross-platform lock. Для каждой
parallel-сессии первая задача выполняется и коммитится в main workspace; только
после успешного commit задачи 2+ распределяются по worktrees, созданным от
validated main `HEAD`. Worktree manager отвечает за безопасное создание,
инспекцию и cleanup, Task Manager — за assignment/status, а Backlog/Execution
Workflow — за bootstrap, fan-out, review, integration и stop conditions.

## Рассмотренные альтернативы

- Разрешить несколько задач в одном workspace — отклонено из-за конфликтов
  незакоммиченных файлов и невозможности надёжно связать checkpoint с задачей.
- Сразу отправлять первую и последующие задачи в worktrees — отклонено, поскольку
  явно утверждённое поведение требует первую задачу в основном workspace.
- Разрешить параллельность только счётчиком active tasks — отклонено: это не
  защищает registry writes, Git branches и cleanup.
- Использовать только serial mode с ручным worktree — отклонено, потому что
  workflow не сможет проверять ownership, recovery и bounded worker limits.

## Объём задачи

### Входит в scope

- serial/isolated_parallel configuration and registry schema;
- cross-platform registry lock and safe Worktree Manager;
- first-task-main bootstrap and worktree fan-out for task 2+;
- Task Manager claims, status, checkpoints, commit evidence and cleanup;
- backlog/execution workflows, CLI, Health, ADR, specifications and migration;
- unit, contract, scenario, Git sandbox, security and acceptance evidence.

### Не входит в scope

- параллельная запись нескольких задач в одну рабочую директорию;
- автоматическое разрешение Git merge conflicts;
- удалённые CI runners, distributed locks, network coordination или UI;
- изменение бизнес-семантики задач, approvals, Memory или Knowledge Graph;
- автоматическое удаление failed worktrees/branches без explicit ownership check;
- изменение уже активной `TASK-0003`.

## Критерии приёмки

- AC1: Serial remains default and current single-slot behavior stays green.
- AC2: Isolated parallel mode has explicit run/worker/workspace validation and no
  concurrent writers in one workspace.
- AC3: Sequence 1 uses main and must commit before sequence 2+ allocation.
- AC4: Sequence 2+ receives unique worktree/branch from validated post-bootstrap
  `HEAD`, with restart/recovery metadata.
- AC5: Registry locking prevents duplicate claims and silent corruption.
- AC6: Worktree tasks can commit independently; conflict/missing evidence stops the
  run without automatic conflict resolution.
- AC7: Cleanup is ownership-checked, preserves failures and never deletes main.
- AC8: CLI, workflows, schemas, docs, tests, security and strict Health agree.

## Ограничения

- Python 3.11+ standard library for runtime paths.
- Git CLI is required for isolated mode.
- Platform-neutral core with Windows/POSIX lock adapters.
- Serial mode is the compatibility fallback.
- Worktrees and branches are task-owned and must be project-root-contained or
  explicitly configured under a validated worktree root.
- Existing user changes and active TASK-0003 remain untouched.

## Риски

- Worktree from stale/dirty main; mitigation: clean-state, commit and base digest
  gates.
- Registry corruption or duplicate claim; mitigation: lock owner token, atomic
  writes, validation and fail-closed stale recovery.
- Merge conflict; mitigation: preserve branches/worktrees and stop for review.
- Unsafe cleanup/path injection; mitigation: canonical containment and ownership
  manifest before every Git mutation.
- Dependency/order drift; mitigation: run identity, sequence and explicit mode
  fallback to serial.

## Plan Review

План покрывает user-selected modes, first-task-main exception, worktree lifecycle,
registry locking, branch/base commit semantics, recovery, cleanup, documentation,
security and executable acceptance. Подход явно подтверждён пользователем:
последовательный режим остаётся доступным, а parallel mode использует main для
первой задачи и worktrees для второй и последующих.

## Открытые вопросы

  утверждены.
