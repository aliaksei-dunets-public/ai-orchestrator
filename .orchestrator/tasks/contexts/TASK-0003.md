# TASK-0003 — Integrate Knowledge Curator into project onboarding

## Исходный запрос

Добавить первичное формирование Knowledge Graph в onboarding и сделать существующий
`knowledge-curator` непосредственным владельцем graph lifecycle.

## Цель

При onboarding target project агент должен подготовить evidence-based graph
proposal, показать его в общем preview, включить его в hash-bound approval и после
approval записать canonical nodes/edges с rollback и Health Check.

## Проблема или потребность

Текущий onboarding создаёт graph stores, но оставляет nodes и edges пустыми.
`knowledge-curator` содержит только краткие правила обслуживания и не описывает
первичную инвентаризацию, proposal handoff и связь с onboarding approval.

## Текущее поведение

Onboarding создаёт `.orchestrator/knowledge/{ontology,nodes,edges}`, а graph nodes
и edges добавляются отдельно через CLI или Python API. Preview onboarding не
содержит graph proposal.

## Ожидаемое поведение

Agent-led onboarding получает optional `knowledge_graph` proposal, core проверяет
его без записи target, merge-ит его с существующим effective graph, включает
canonical file changes в `plan_hash`, а apply атомарно записывает и валидирует
результат. Пустой proposal остаётся корректным no-op.

## Анализ

Existing `knowledge-curator` уже зарегистрирован как bundled canonical skill, поэтому
новый дублирующий skill не нужен. Граница ответственности: project-onboarding
управляет target bootstrap и approval, knowledge-curator — graph discovery,
provenance, ontology, conflict, merge и rebuild semantics. Proposal contract нужен
для безопасной передачи результата от агента к deterministic core.

## Выбранный подход

Расширить существующий `knowledge-curator`, добавить non-mutating proposal/merge
слой в core и встроить graph content в существующий onboarding plan/apply/rollback.
Сохранить backward compatibility: отсутствие proposal не изменяет прежнее
поведение.

## Рассмотренные альтернативы

- Создать отдельный `knowledge-onboarding` skill — отклонено из-за дублирования
  graph ownership и риска расхождения правил.
- Автоматически сканировать весь проект без proposal — отклонено из-за слабой
  provenance и риска ложных nodes/edges.
- Записывать graph после onboarding отдельным шагом — отклонено, потому что
  graph должен входить в общий preview, approval и rollback.

## Объём задачи

### Входит в scope

- graph proposal schema и deterministic merge;
- onboarding preview/hash/apply/rollback/validation;
- расширение canonical `knowledge-curator` и project-onboarding skills;
- schemas, specifications, guides и roadmap;
- focused, scenario, contract, acceptance, Health, audit и security evidence.

### Не входит в scope

- embeddings, vector database и network synchronization;
- автоматическое извлечение всех сущностей из произвольного кода;
- cross-project memory/knowledge;
- изменение ontology semantics за пределами additive project terms;
- UI для ручного редактирования графа.

## Затрагиваемые компоненты

- `orchestrator/knowledge.py` и новый `orchestrator/knowledge_bootstrap.py`;
- `orchestrator/onboarding_workflow.py`;
- `skills/bundled/knowledge-curator/SKILL.md`;
- `skills/system/project-onboarding/SKILL.md`;
- schemas, registries, specifications, guides and tests.

## Критерии приёмки

- AC1: `knowledge_graph` proposal version 1 валидируется и входит в onboarding preview и `plan_hash`.
- AC2: Source provenance, ontology, conflicts, supersede cycles и effective endpoints валидируются до записи.
- AC3: Approved apply сохраняет canonical graph, rebuild-ит indexes и откатывает graph вместе с onboarding при ERROR/CRITICAL.
- AC4: Отсутствующий или пустой proposal является idempotent no-op; существующие APIs совместимы.
- AC5: `knowledge-curator` владеет graph lifecycle, onboarding — bootstrap/approval boundary.
- AC6: Skills, schemas, specs, guides и component contracts согласованы.
- AC7: Focused/scenario/contract/acceptance checks покрывают valid, invalid, stale, rollback, idempotency и retrieval cases.
- AC8: Strict Health, documentation checks, audit и security review не имеют ERROR/CRITICAL.

## Ограничения

- Python 3.11+ и standard library runtime.
- Platform-neutral core.
- Не редактировать generated skill projections вручную.
- Не коммитить tasks registry, proposals, indexes, backups, checkpoints, releases.
- Canonical source остаётся source of truth.

## Риски

- Ложные graph assertions: mitigation — proposal preview, provenance и approval.
- Потеря существующих nodes/edges: mitigation — stable-ID merge и conflict rejection.
- Частичный apply: mitigation — общий backup/rollback onboarding.
- Stale approval: mitigation — plan hash и target fingerprint.
