# Migration 1.4: Task finalization

## Completion contract change

New transitions to `done` require a completion-ready Task Finalization receipt.
Before commit, the execution workflow must:

1. collect normalized changed paths;
2. obtain documentation dispositions for all mapped documents;
3. obtain an explicit Knowledge Curator proposal, including a valid empty no-op;
4. create/promote memory proposals or resolve hash-bound approvals;
5. write a receipt through `orchestrator-task finalize`.

Minimal `finalization.json`:

```json
{
  "changed_paths": ["orchestrator/example.py", "docs/example.md"],
  "documentation_dispositions": [
    {
      "document": "docs/example.md",
      "status": "updated",
      "reason": "",
      "evidence_ref": "docs/example.md"
    }
  ],
  "knowledge_proposal": {
    "schema_version": 1,
    "nodes": [],
    "edges": []
  },
  "memory_candidates": []
}
```

After commit:

```powershell
.\.venv\Scripts\orchestrator-task.exe complete TASK-0006 `
  --finalization-receipt .orchestrator/tasks/finalization/TASK-0006.json
```

For an isolated worktree, `--commit-evidence` and `--repository-root` remain
required.

## Compatibility

- Existing `done` records without `finalization` remain valid for read/list,
  Health and migration.
- A new `complete` call without a receipt returns
  `FINALIZATION_REQUIRED`/exit code `10`.
- `cancel` does not require a receipt and preserves the checkpoint.
- The receipt is stored in `.orchestrator/tasks/finalization/` and excluded from Git.
- Task Registry stores only the receipt hash, changed-paths digest, and completion
  timestamp.

## Pending approvals

Instruction and non-authoritative memory candidates create proposals, not
canonical entries. Without approval the receipt has
`memory_status=waiting_user` and `ready_for_completion=false`; backlog stops
before commit. After approval or rejection, finalization runs again with the
same inputs and reuses the proposal idempotently.

## Rollback

Do not delete canonical memory history or knowledge records manually. Before
commit, only the task-owned operational receipt may be removed before retrying
execution. After commit, use Git revert for runtime/docs/graph changes,
`disable`/`supersede` for append-only memory, and a new graph proposal for
knowledge correction.
