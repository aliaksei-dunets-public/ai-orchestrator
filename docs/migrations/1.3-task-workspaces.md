# Migration 1.3: Task workspaces

## Compatibility

Existing Task Registry records without `assignment` remain valid and execute in
`serial` mode. The default is:

```yaml
execution:
  mode: serial
  max_workers: 1
  worktree_root: .orchestrator/worktrees
```

Serial uses the primary workspace and retains the branch already selected by
the user. It does not create or switch to a task branch or Git worktree, and it
does not integrate or clean up task-owned Git state. This is an
orchestrator-agent policy, not a forced `main` checkout or a restriction on an
external Git client.

## Enable isolated parallel

For a new run, set a unique `run_id`, `max_workers` from 2 through 16, and
`worktree_root`. The first task must finish with a commit in main. Task Manager
can then assign backlog tasks to task-owned worktrees.

Example:

```powershell
.\.venv\Scripts\python.exe -m orchestrator.task_cli claim-next --json `
  --mode isolated_parallel --run-id release-13 --max-workers 3 `
  --worktree-root .orchestrator/worktrees --repository-root .
```

For an isolated task, `complete` requires the full commit SHA:

```powershell
.\.venv\Scripts\python.exe -m orchestrator.task_cli complete TASK-0007 `
  --commit-evidence <40-character-sha> --repository-root .
```

Inspect an assignment with `orchestrator workspace inspect TASK-ID`. Cleanup
requires a terminal outcome and removes only a worktree with a matching
ownership manifest. Failed worktrees are preserved.

## Rollback

Stop the isolated run, preserve unfinished worktrees, and switch
`execution.mode` back to `serial`. Do not remove a worktree manually until its
branch and ownership manifest are verified. Assignment records may remain for
recovery; legacy serial records need no conversion.
