# Универсальный оркестратор разработки

## Архитектурная спецификация и поэтапный план реализации

**Статус документа:** начальная спецификация продукта  
**Версия:** 0.3  
**Язык:** русский  
**Назначение:** исходный документ для создания отдельного Git-репозитория универсального оркестратора, который может подключаться к различным проектам и адаптироваться к их технологии, архитектуре и платформе выполнения без изменения собственного ядра.  
**Детальная спецификация уровня задач:** `task-layer-specification-ru.md`

---

## 1. Краткое описание

Универсальный оркестратор — это переносимый набор инструкций, workflow, навыков, реестров, шаблонов и правил, который управляет выполнением задач разработки.

Оркестратор не должен быть жёстко привязан:

- к конкретному проекту;
- к языку программирования;
- к технологическому стеку;
- к платформе выполнения агента;
- к конкретному MCP-серверу;
- к конкретному формату проектной документации.

Оркестратор поставляется как отдельный Git-репозиторий и подключается к целевому проекту одним из двух способов:

1. **Managed mode** — подключение через Git submodule с возможностью обновлять ядро оркестратора.
2. **Standalone mode** — однократное копирование оркестратора в проект с последующей независимой доработкой без обязательной синхронизации с исходным репозиторием.

Внутри целевого проекта универсальное ядро расширяется тремя внешними слоями:

1. профилем платформы выполнения;
2. технологическим профилем;
3. контекстом конкретного проекта.

Ядро оркестратора остаётся неизменным. Проектные различия описываются конфигурацией, профилями и локальными overrides.

## 2. Цели продукта

### 2.1. Основные цели

Оркестратор должен:

- брать задачи из простого списка задач;
- выбирать подходящий workflow в зависимости от размера, риска и типа задачи;
- формировать план выполнения;
- реализовывать задачу;
- создавать и запускать тесты;
- выполнять аудит результата;
- проводить plan review, task review, code review и security review;
- предоставлять результат пользователю для проверки, когда это требуется;
- обновлять документацию;
- обновлять проектную память и граф знаний;
- формировать отчёт о сессии;
- предлагать улучшения собственных навыков, инструкций и workflow;
- выполнять последовательность задач из backlog в управляемом цикле;
- адаптировать своё поведение к возможностям конкретной платформы выполнения;
- проверять целостность, совместимость и готовность установленного оркестратора в целевом проекте через Health Check.

### 2.2. Дополнительные цели

- Модульность.
- Прозрачность решений.
- Возможность ручного контроля.
- Возможность постепенного внедрения.
- Возможность тестирования каждого навыка отдельно.
- Возможность регрессионного тестирования всего оркестратора.
- Возможность использовать ранние версии оркестратора в реальных проектах.
- Возможность развивать оркестратор итерационно, добавляя по одному навыку или workflow.

---

## 3. Не-цели

На начальных этапах оркестратор не должен:

- быть сложной системой управления проектами;
- заменять Jira, Linear, GitHub Projects или аналогичный продукт;
- хранить подробную телеметрию каждого действия агента;
- создавать отдельный каталог артефактов для каждой маленькой задачи;
- автоматически изменять собственное ядро без подтверждения пользователя;
- автоматически принимать архитектурные решения высокого риска;
- выполнять бесконечный автономный цикл без ограничений и контрольных точек;
- требовать отдельный установщик;
- зависеть от конкретной модели, IDE или провайдера AI.

## 4. Архитектурные принципы

### 4.1. Ядро не знает проект

Ядро описывает универсальные правила:

- как выбирать задачу;
- как строить план;
- как выполнять проверки;
- как маршрутизировать навыки;
- как формировать отчёт;
- как работать с памятью;
- как предлагать улучшения.

Ядро не содержит:

- имён конкретных пакетов;
- неймспейсов проекта;
- бизнес-правил;
- путей проекта;
- конкретных команд тестирования;
- конкретных URI;
- конкретных MCP-инструментов.

### 4.2. Конфигурация важнее жёсткой логики

Поведение оркестратора должно определяться декларативно:

- включёнными навыками;
- активными workflow;
- правилами маршрутизации;
- профилем платформы;
- технологическим профилем;
- проектным контекстом;
- локальными overrides.

### 4.3. Навыки изолированы

Каждый навык должен иметь:

- отдельное назначение;
- чёткие входы;
- чёткие выходы;
- предусловия;
- критерии успеха;
- ограничения;
- собственные тестовые сценарии.

### 4.4. Workflow собираются из навыков

Workflow не дублируют логику навыков. Они определяют:

- последовательность;
- условия запуска;
- обязательность шагов;
- точки остановки;
- переходы между состояниями;
- обработку ошибок;
- правила повторного выполнения.

### 4.5. Самоулучшение только через предложения

Оркестратор может:

- собирать наблюдения;
- обнаруживать повторяющиеся проблемы;
- формировать рекомендации;
- создавать proposal на изменение навыка, инструкции или workflow.

Оркестратор не должен автоматически применять такие изменения без явного подтверждения пользователя.

### 4.6. Минимальная достаточность

Для небольших задач применяется короткий workflow. Полный цикл запускается только тогда, когда сложность, риск или влияние задачи этого требуют.

### 4.7. Контролируемая автономность

Автономная обработка backlog должна быть конечной и управляемой:

- ограниченное число задач за запуск;
- остановка при блокере;
- остановка при высоком риске;
- остановка при необходимости пользовательского решения;
- отсутствие автоматического обхода обязательных проверок.

## 5. Модель слоёв

Оркестратор состоит из следующих логических слоёв.

### 5.1. Layer 1 — Core

Содержит универсальные правила и жизненный цикл оркестратора.

Ответственность:

- загрузка конфигурации;
- определение активных профилей;
- регистрация навыков и workflow;
- маршрутизация задачи;
- управление состоянием выполнения;
- контроль обязательных проверок;
- формирование результатов и отчётов.

### 5.2. Layer 2 — Task Layer

Уровень задач разделён на четыре независимые части:

1. **Task Creator** — анализирует запрос и создаёт подготовленный Task Context.
2. **Task Context** — хранит спецификацию, критерии приёмки, план и результат выполнения.
3. **Task Manager** — хранит очередь, внешний статус и ссылку на Task Context.
4. **Task Execution Workflow** — реализует задачу и проводит обязательные проверки.

Task Manager остаётся лёгким автоматом состояний. Он отвечает только за:

- регистрацию готовой задачи;
- выделение ID;
- чтение списка задач;
- выбор следующей задачи;
- атомарное взятие задачи в работу;
- проверку допустимости перехода;
- изменение статуса;
- фиксацию краткой причины ожидания или блокировки.

Task Manager не хранит план, acceptance criteria, результаты review или перечень изменённых файлов. Эти данные находятся в Task Context.

Подробный нормативный контракт описан в `task-layer-specification-ru.md`.

### 5.3. Layer 3 — Workflow Engine

Исполняет сценарии обработки задачи.

Ответственность:

- выбор workflow;
- выполнение шагов;
- проверка предусловий;
- контроль переходов;
- повтор шагов при исправлении замечаний;
- остановка на approval gate;
- адаптация workflow к платформенным ограничениям.

### 5.4. Layer 4 — Skills

Набор атомарных способностей оркестратора.

Примеры:

- task selection;
- task planning;
- plan review;
- implementation;
- test generation;
- test execution;
- task review;
- code review;
- security review;
- documentation update;
- knowledge extraction;
- memory capture;
- session reporting;
- orchestrator health check;
- orchestrator audit;
- improvement proposal.

### 5.5. Layer 5 — Registries

Реестры описывают доступные сущности.

Минимальные реестры:

- skill registry;
- workflow registry;
- capability registry;
- platform profile registry;
- technology profile registry;
- template registry;
- policy registry.

### 5.6. Layer 6 — Platform Profiles

Профиль платформы выполнения описывает технические возможности среды, в которой работает оркестратор.

Примеры платформ:

- OpenAI Codex;
- GitHub Copilot;
- Claude Code;
- Antigravity;
- локальный агент;
- IDE-агент;
- CI-агент.

Профиль платформы отвечает на вопросы:

- доступны ли sub-agents;
- доступно ли параллельное выполнение;
- доступны ли MCP-инструменты;
- поддерживаются ли virtual URI;
- можно ли читать и изменять локальные файлы;
- доступен ли Git;
