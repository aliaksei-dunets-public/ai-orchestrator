# Повторный аудит AgentGraphRuntime: оценка замечаний

**Статус:** проверенная оценка текущего кода и контрактов, 2026-09-18. Исправления кода и новые задачи в рамках этой проверки не выполнялись. Это не повторная приёмка TASK-0034 и не полный независимый аудит проекта.

**Основание:** переданный пользователем отчёт из вложения `99e61862-47ab-4e90-a58b-8ac1ad82ef13/Pasted text.txt`, исходный сценарий аудитора, действующие контракты, project-status и собственные изолированные воспроизведения. Незавершённые изменения execution gates в рабочем дереве учтены как текущий код, а не автоматически принятый результат.

## Что действительно требует работы

1. Уточнить и реализовать требования к выходам для разных исходов узла. Сейчас обязательный итоговый выход препятствует вопросу, блокировке и сообщению об ошибке. Ограничение подтверждено, но оценка «критический дефект» завышена: текущая реализация соответствует написанному контракту, а основные графы AgentPreparation/AgentExecution не задают такие обязательные выходы.
2. Исправить обнаруженную при проверке несовместимость запроса подтверждения KnowledgeRefreshNode с протоколом паузы AgentGraphRuntime. Это уже конкретный дефект композиции реализованных компонентов: результат с `awaiting_confirmation` и `wait` runtime не принимает.
3. Убрать оставшиеся устаревшие описания callback API в навигационной документации. В `docs/README.md` до сих пор указаны `step`, `resume`, `resume_blocked`, хотя поддерживается агентский API.

Пересчёт бюджета, прямой доступ runtime к Task Manager и перепривязка старых результатов к новому определению задачи не обоснованы как исправления обнаруженных ошибок. MCP transport относится к запланированной поставке.

## Требования к выходам: объём оправданной доработки

В [общем validator](../../orchestrator/runtime_contracts.py) required outputs проверяются независимо от outcome. В [структурном контракте](../architecture/graph-runtime-contract.md) и [агентском контракте](../architecture/agent-runtime-contract.md) это текущее правило прямо закреплено. Поэтому проблема находится одновременно в выразительности модели и ожидаемой семантике итогового выхода, а не в расхождении кода с документацией.

В [графе подготовки](../../orchestrator/preparation_primitives.py) и [графе исполнения](../../orchestrator/agent_execution.py) `required_outputs` пусты; семантические требования проверяются фасадами. В [knowledge graph](../../orchestrator/knowledge_refresh_node.py) обязательный `result` является структурированным отчётом любого исхода и действительно возвращается, включая ошибку и запрос подтверждения. Его нельзя считать фиктивным итоговым документом.

Предложение аудитора просто пропускать проверку для трёх имён исходов решает узкий случай, но не определяет требования для `approved`, `failed`, `retryable_failure`, доменных ошибок и обязательных диагностических выходов. Нужна явная политика: какие outputs обязательны для какого outcome. Возможен минимальный вариант с обязательными итоговыми outputs только на обозначенных успешных исходах и отдельными требованиями к диагностике/паузам. Выбранный вариант следует согласовать как изменение контракта и описать в гайде.

Критерии исправления:

- Вопрос и блокировка до создания итогового артефакта принимаются и возобновляются штатно.
- Ошибка без итогового успешного артефакта может завершить узел; обязательная диагностика проверяется по своему контракту.
- Успешный исход без обязательного выхода по-прежнему отклоняется.
- Сохраняются проверки node/outcome, формы артефактов, JSON, wait, revision и бюджета; исключение из required outputs не отключает остальные guards.
- Отклонённый результат не изменяет run; действующие требования к служебному `result` KnowledgeRefreshNode сохраняются.
- Добавляются предметные проверки общего validator и submit_result, включая доменные успешные/ошибочные outcomes.

Минимальное воспроизведение текущего ограничения из корня проекта:

```python
from orchestrator import AgentGraphRuntime, Graph, Node, NodeResult, WaitState

node = Node("work", "input/v1", "result/v1", ("needs_input", "success"),
            {"needs_input": "work", "success": "succeeded"}, ("plan",))
runtime = AgentGraphRuntime()
run = runtime.create_run(Graph("probe", 1, "work", {"work": node}), {})
runtime.submit_result(run.run_id, NodeResult(
    "work", "needs_input",
    wait=WaitState("WAIT-1", "work", "user_input", question="Какой режим?")),
    expected_revision=1)
# RuntimeError: contract_violation, missing=["plan"]. Run остаётся created/revision=1.
```

## Дополнительный подтверждённый дефект: knowledge confirmation

[KnowledgeRefreshNode.execute](../../orchestrator/knowledge_refresh_node.py) при `mode="full", authorization="required"` без одобрения возвращает `NodeResult(outcome="awaiting_confirmation", data={"result": ...}, wait=...)`. [AgentGraphRuntime](../../orchestrator/agent_runtime.py) допускает wait только для `needs_input` и `blocked`. Передача такого результата в собственный `node.graph` завершается `contract_violation: Этот outcome не допускает wait`, хотя обязательный `result` уже присутствует. Состояние run не меняется; полная переиндексация не выполняется.

Это отдельная проблема, которую предлагаемое исключение из required outputs не устранит. Она воспроизведена на настоящем KnowledgeRefreshNode и настоящем runtime с детерминированным service double без Graphify и изменений project knowledge pointer.

Текущий [knowledge gate в AgentExecution](../../orchestrator/agent_execution.py) также передаёт исход и wait в runtime. Его [graph definition](../../orchestrator/execution_gates.py) объявляет `awaiting_confirmation` обычным исходом с переходом в `failed`; поддержка паузы здесь тоже требует согласования. Это установленный по коду риск того же пути; полный сценарий gate→одобрение→refresh в этой оценке не исполнялся.

Приоритет — исправить до включения полной переиндексации с пользовательским подтверждением через runtime/gates. Требуется согласовать transport outcome и доменный status: например, runtime получает `needs_input`, а `data.result.status` сохраняет `awaiting_confirmation`. После явного ответа должны выполняться обычные wait guards и отдельный повторный вызов узла. Расширение runtime новыми специальными outcomes возможно только с обновлением общего протокола.

Обязательная регрессия: `execute без одобрения → submit → waiting_input → resume с явным решением → execute с одобрением → submit`. Отказ не должен запускать full refresh; одобрение без проверяемого decision ref не должно обходить policy. Для execution gates нужна аналогичная интеграционная проверка. Сейчас [шесть tests узла](../../tests/test_knowledge_refresh_node.py) проверяют выдачу wait, но не принятие его runtime.

## Бюджет и изменение определения

В [контракте бюджета](../architecture/agent-runtime-contract.md) все принятые NodeResult, включая вопросы и ошибки, расходуют slot; resume/cancel не расходуют. Собственная проба: при двух slots вопрос и последующий успех завершают одноузловой граф; при одном slot вопрос принимается, после ответа доступна только отмена. Аналогично с blocker и per-node limit. Это ограничение успешного продолжения, а не deadlock блокировок или зависание сервиса.

Если вообще не учитывать ожидания, цикл вопросов перестанет ограничиваться max_results, хотя история продолжит расти. Если выдавать бесплатный slot после каждого resume, можно аналогично обходить общий/per-node лимит. Отдельная продуктовая политика резервирования terminal slot потребовала бы самостоятельного дизайна: обычный результат узла не обязательно завершает весь процесс. Предупреждение host при нулевом бюджете — разумное необязательное улучшение.

Обязанность caller читать definition_version перед task-bound мутацией указана в контракте. [AgentPreparation](../../orchestrator/agent_preparation.py) и [его primitives](../../orchestrator/preparation_primitives.py) сверяют реальную task.version; reconcile допускает внешние метаданные, но отвергает изменение определения. [AgentExecution](../../orchestrator/agent_execution.py) также проверяет карточку, preparation binding и claim. Они не могут предотвратить произвольное обходное использование generic API чужим caller; интеграция должна пользоваться проверенными фасадами.

Утверждение «старый run необратимо блокируется» неточно: cleanup/cancel после definition drift предусмотрен в обоих фасадах. В тесте подготовки подтверждены отмена и освобождение active_run_ref. Изменение заголовка через публичный `update_metadata` не меняет definition_version и допускает reconcile. [Task Manager](../../packages/task-manager/src/orchestrator_task_manager/service.py) не позволяет refine определения в статусе active. Уточнение цели/критериев требует новой проверки подготовки; автоматически маркировать старый plan/review/package актуальной версией нельзя. Необходимость повторной подготовки не означает автоматическое удаление всех прежних артефактов или запрет их использовать как исходный материал.

Полный проектный suite, ресурсоёмкий benchmark и сквозной внешний MCP-сценарий не повторялись: они не нужны для воспроизведения этих двух проблем и не объявляются проверенными этой оценкой.
