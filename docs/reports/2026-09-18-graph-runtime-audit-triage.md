**Статус:** анализ текущей реализации и основание для задачи исправлений; исправления runtime не выполнены.

**Дата:** 2026-09-18.

Ниже сохранён исходный разбор аудита; рекомендации ремонтировать и сохранять legacy API заменены [новым объёмом задачи](../plans/2026-09-18-remove-callback-runtime-scope.md). После разрешения приступить к исполнению удаление выполнено и проверено; [результаты кандидата](2026-09-18-task-0034-callback-removal.md).

**Задача устранения:** `TASK-0034`, первоначально создана для исправления дефектов; после уточнения пользователя называется `[HIGH] Удалить callback GraphRuntime и актуализировать документацию`. Создана через публичный CLI Task Manager в статусе `created`; исполнение не запускалось.

Источник — переданный пользователем отчёт «Searched for files: *runtime* Listed directory orchestrator Viewed workflow_run…», attachment `2ee219ac-3f08-491c-9c1a-3ba47d334284/Pasted text.txt`. ## Решение по каждому замечанию

Нумерация соответствует исходному отчёту. «Подтверждено» означает дефект или наблюдаемую потерю данных, «уточнение» — недостаточно ясное описание существующего поведения, «оценка» — риск, требующий измерений, а не доказанная уязвимость.

| Пункт | Решение | Основание и действие |
| --- | --- | --- |
| 1.1: answer против resolution для blocker | Предусмотренное различие | Callback API сохранён для совместимости; agent API отдельно требует resolution и ведёт историю. Не объединять API ради одинаковых сигнатур. |
| 1.2: синтез blocker wait против обязательного wait | Предусмотренное различие | Agent API намеренно не угадывает причину; legacy поддерживает прежний fallback. Уточнить таблицу совместимости, сохранить поведение. |
| 1.3: терминальные имена узлов | Подтверждено | Graph/legacy принимают имя `succeeded`, но переход на него завершает процесс вместо исполнения узла. Запретить неоднозначные определения до создания legacy run; проверить все три имени. |
| 1.4: Python-объекты против строгого JSON | Предусмотренное различие | Legacy — Python callback API; agent API имеет отдельную JSON-границу. Существование legacy MCP/JSON API, которое ломается от этого, аудитом не доказано. Документировать границу, не вводить совместимость ценой запрета прежних Python-входов. |
| 1.5: бесконечный цикл legacy | Преувеличено | `step` выполняет ровно один callback, внутреннего executor loop нет. Повторные вызовы без лимита возможны у caller; budgets уже есть в новом пути. Не добавлять скрытый цикл или новый legacy scheduler. |
| 2.1: сигнатура create_run | Подтверждено; документация исправлена при анализе | Реальный task_ref keyword-only. Также исправлены keyword-only wait_id/node_id в resume/resume_blocked. Позиционный task_ref не добавлялся. |
| 2.2: transitions для needs_input/blocked | Уточнение; документация исправлена при анализе | Сохранение текущего узла соответствует обоим pause/resume контрактам. Таблица transitions формально обязательна, но специальные исходы не используют её цель. Маршрутизация на ask/escalation противоречила бы текущей модели. |
| 2.3: retryable_failure | Уточнение; документация исправлена при анализе | Это обычный объявленный исход с явным переходом, встроенных retry policy/attempt counters нет. Убрано впечатление существующего автоматического retry; безопасность эффекта остаётся у caller. |
| 2.4: потеря cancel reason | Подтверждено как недостаток диагностики | Legacy валидирует reason и выбрасывает его; snapshot содержит только cancelled. Предусмотреть доступ к причине с совместимым публичным контрактом, не менять молча существующую serialization. |
| 3.1: параллельные действия legacy | Подтверждено | Нет lock, reservation или revision guard. Два step могут вызвать один callback одновременно, хотя контракт запрещает одновременное исполнение узла. Нужна локальная защита исполнения и публикации; не multiprocess lease. |
| 3.2: отмена затирается callback | Подтверждено, высокий приоритет | Воспроизведено: cancel возвращает cancelled, завершение callback публикует succeeded. Отмена должна оставаться терминальной; возврат или исключение старого callback не должны перезаписать её. |
| 3.3: потеря ответа legacy | Факт подтверждён, обязательная история не обещана | После успешного resume wait очищается, ответ сохраняется только если callback положил его в data. Agent API уже сохраняет resumed_wait/history. Документировать ответственность legacy caller и проверить доставку/очистку; не переносить всю agent history в legacy. |
| 4.1: deep-copy history | Обоснованный риск; нужна оценка | `submit_result` копирует run в working, `_publish` копирует его для возвращаемого snapshot. В самом `_publish` одна полная копия, а не две. Совокупная работа по истории может расти квадратично; строки deepcopy обычно переиспользует, поэтому пример с размером диффа не доказывает такой же объём новых аллокаций. Измерить вложенные JSON и строки, отдельно peak memory и latency; сохранить изоляцию снимков. |
| 4.2: budget exhaustion deadlock | Предусмотренная политика, не дедлок | Контракт явно учитывает needs_input/blocked в бюджете и описывает последний slot. Resume принимается, новый result запрещён, cancel доступен. Не сбрасывать counters и не обходить budget. |
| 4.3: подделка artifact refs | Граница ответственности, не доказанная уязвимость runtime | Runtime проверяет форму; payload/hash/version проверяет ArtifactRepository и профильный facade. Это явно закреплено в обоих контрактах и тестах. Не вводить файловое хранилище в generic runtime; semantic gate не должен принимать форму ref за доказательство. |
| 4.4: input/output contract без схемы | Граница ответственности | Это ссылки на контракты; семантическую проверку выполняют владельцы контрактов. Общий validator проверяет node/outcome/mappings/required_outputs/artifact shape. Универсальный schema registry не входит в текущий срез. |
| 4.5: неограниченные строки | Обоснованный ресурсный риск; exploit не доказан | Это локальный Python API без показанного недоверенного сетевого входа. Число результатов ограничено в agent API, размер payload — нет. Оценить размер history/payload и boundary limits вместе с 4.1; произвольные лимиты каждого текстового поля без измерений не вводить. |
| 5: отсутствие persistence | Известное ограничение этапа | Оба runtime in-memory по действующим контрактам и roadmap; checkpoints/restart recovery отложены. Восстановление active task не становится функцией Graph Runtime из-за регистрации ссылки. Не добавлять durable runtime или новую SQLite в задачу исправлений. |

## Проверки

Выполнены изолированные Python-пробы в памяти, без мутаций задач, файлов артефактов или внешних эффектов:

1. Callback приостановлен через `threading.Event`; другой поток вызывает cancel, затем callback возвращает success. Получено `after_cancel=cancelled`, `after_executor=succeeded`, ошибок нет. Это прямое воспроизведение 3.2.
2. Граф содержит узлы `a` и `succeeded`; `a.success` указывает на `succeeded`. Legacy создаёт run и завершает его с `state=succeeded`, `current_node=null`, не вызывая второй узел. Это воспроизведение 1.3 для одного из зарезервированных имён.
3. `inspect.signature(GraphRuntime.create_run)` подтверждает `*, task_ref=None`; reason отмены отсутствует в возвращаемом `WorkflowRun.to_dict()`.
4. Agent run с `max_results=1` принимает needs_input, затем resume; `remaining_results=0`, `actions=[cancel]`. Это ожидаемая политика, а не зависание lock.
5. Публичный CLI `validate` перед созданием задачи вернул `ok=true`, `result=[]`. Полный suite не запускался: код runtime не менялся, эта работа не является повторным полным аудитом интеграции или benchmark.

## Объём задачи устранения

Высокий приоритет: защита legacy run от одновременного исполнения и устаревшей публикации после cancel; отклонение терминальных имён; доступная причина отмены с явной совместимостью. Дополнительно — таблица различий API, ясные границы wait/answer/retry/JSON/semantic validation, предметные регрессии и измеренная оценка history/payload с адресной мерой при подтверждённой проблеме.

Критерии сформулированы по результатам этого анализа, а не выданы за отдельно согласованный пользователем дизайн. Перед реализацией задача должна пройти штатную подготовку; сохранение `created` не означает `ready` или разрешённый claim. Персистентность, объединение runtimes, новые внешние адаптеры и обход budgets исключены. Изменения соседних текущих задач не требуются.
