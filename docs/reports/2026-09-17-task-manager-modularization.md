# TASK-0024: разделение Task Manager на модули

**Статус:** реализация проверена; результат подготовлен к отдельной пользовательской приёмке.

## Результат

Монолит `task_manager.py` на 1444 строки заменён совместимым фасадом на 24 строки. Выделены contracts (107), migrations (111), repository (297), service (748), storage_transfer (195) и diagnostics (85). Жизненный цикл остаётся в одном сервисе; отдельные mixin-классы и новые модели не вводились. [Дизайн](../plans/2026-09-16-task-manager-modularization-design.md) согласован пользователем после аудита.

Сохранены три публичных класса из пакета и старого модуля, именованные и wildcard-импорты прежних констант, параметры/аннотации существующих публичных методов, JSON, коды ошибок, CLI и схема SQLite версии 5. Новых внешних зависимостей нет. Переэкспорты приватных helper-функций остаются доступными, но точки monkeypatch обновлены в тестах на модули использования: service и storage_transfer.

Сервис не выполняет SQL и не вызывает приватные методы репозитория. SQL остаётся в инфраструктурных компонентах. Для диагностики и экспорта создана явная read-only граница `read_transaction`: query_only, BEGIN DEFERRED и закрытие соединения. Restore вызывает самостоятельный запуск миграций на временной копии. Атомарная запись карточки/события/операции, ready-guard и безопасность backup/restore сохранены.

## Скорость

Windows 11 26200, Python 3.12.14, SQLite 3.53.1. Сначала выполнены обычные последовательные замеры на 100/1000 задач. На 1000 медиана страницы изменилась 0.909 → 1.335 мс, validate 12.541 → 16.342, export 35.925 → 48.000, summary 2.711 → 3.706. Даже неизменённый SHA-256 100 MiB колебался 57.567 → 87.304 мс. Поэтому эти отдельные прогоны не доказывают эффект разделения и не использованы как основание вывода об ускорении или регрессии.

Затем проведены два парных прогона AB/BA в одном процессе на одной временной базе: 1000 created-задач с одним событием, короткие карточки, 3 прогрева и 30 повторов каждой реализации. Итоговый прогон, p50 / p95 в миллисекундах:

| Операция | До | После |
| --- | --- | --- |
| Страница 100 | 0.739 / 0.829 | 0.743 / 0.816 |
| Полный список | 6.175 / 8.982 | 6.455 / 8.288 |
| Summary | 2.493 / 2.713 | 2.511 / 2.694 |
| Validate | 9.598 / 9.994 | 9.642 / 9.894 |
| Export | 31.393 / 33.835 | 31.428 / 34.758 |

В первом парном прогоне изменение медиан составляло около 0–2%, во втором — около 0–5%; наибольшее отличие второго — полный список (+4.5%), без ухудшения его p95. Это небольшая выборка, не доказательство статистической эквивалентности. Выраженного общего замедления в парных проверках не обнаружено; ускорение не заявляется.

Отдельно проверен полный запуск CLI `api` в свежем Python -S из прежнего и нового wheel с чередованием AB/BA: 4 прогрева, 20 измерений. Для итогового wheel p50 118.397 → 121.506 мс (+2.6%), p95 127.008 → 126.082 мс. В предыдущем прогоне отличие медиан было +1.5%. Команда не открывает базу; это замер запуска/импорта/JSON, не задержка всех команд.

Замеры не характеризуют большой объём истории, холодный диск, другие платформы или множество одновременно работающих процессов. Основная польза разделения — проверяемые границы и сопровождение; алгоритмической оптимизации этот этап не обещает.
