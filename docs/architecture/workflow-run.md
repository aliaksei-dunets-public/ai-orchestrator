# Workflow Run: граф для агента в реальном времени

**Статус:** упрощённая архитектура v1 подтверждена пользователем, 2026-09-15. Graph Runtime ещё не реализован. Заменяет предыдущую модель устойчивого runtime с обязательным транзакционным хранилищем.

## Назначение

Граф управляет последовательной работой одного агента: задаёт следующий узел, его входы, допустимые результаты и переходы. Это не фоновый планировщик и не система управления пулом исполнителей.

```text
Агент получает входы узла
→ выполняет шаг
→ возвращает структурированный результат
→ runtime проверяет результат
→ граф выбирает следующий узел
```

Агент или платформенный адаптер выполняет операцию; runtime не обязан самостоятельно запускать модель. Ядро не зависит от конкретной платформы. Подграф возвращает результат вызывающему графу, а не управляет его маршрутом.

## Состояние запуска

Один запуск ведётся в памяти одной активной сессии агента. Минимальная логическая модель:

| Поле | Смысл |
| --- | --- |
| `run_id` | Идентификатор процесса для ссылок и диагностики |
| `task_ref` | Задача Task Manager; может отсутствовать до регистрации запроса |
| `graph_ref`, `graph_version` | Определение графа, неизменное на время запуска |
| `phase` | `request`, `preparation` или `execution` |
| `state` | `created`, `running`, `waiting_input`, `blocked`, `succeeded`, `failed` или `cancelled` |
| `current_node` | Узел, который выполняется или ожидает продолжения |
| `inputs`, `results` | Структурированные входы и принятые результаты |
| `wait` | Вопросы или причина блокировки и ответ для текущего ожидания |

Это логическая модель состояния будущего runtime. Формат узлов и результатов следует согласовать с существующими контрактами Development Workflow; runtime API ещё не реализован. Один узел выполняется за раз. Переход к следующему запрещён, пока текущий шаг не вернул допустимый результат.

Task Manager владеет задачей, а runtime — текущим процессом. Завершение подготовки не означает завершение задачи. Граница `ready` сохраняется; подготовка и исполнение имеют отдельные запуски.

## Результат узла и маршрутизация

Минимальная оболочка:

```yaml
node_result:
  node_id: plan_review
  outcome: approved
  artifacts:
    plan_review:
      contract: plan-review/v1
      value:
        status: approved
```

Входы и обязательные выходы должны быть определены в контракте конкретного узла. Общие исходы при необходимости: `success`, `needs_context`, `needs_input`, `blocked`, `retryable_failure`, `failure`. Предметные исходы вроде `approved`, `changes_required` и `fresh` уже описаны в контрактах соответствующих этапов.

Runtime проверяет принадлежность результата текущему узлу, допустимость исхода и обязательные выходы. Неизвестный исход не считается успехом. Маршрут выбирается из определения графа; поле `route.target` в исходных материалах не является командой агента.

## Ожидание и ошибки

При `needs_input` агент задаёт вопрос и останавливает продвижение графа. Ответ относится к текущему ожиданию; после проверки тот же узел получает ответ и возвращает новый результат в той же сессии. При `blocked` нужно устранить причину перед повторным вызовом узла. Подробнее: [пауза и возобновление](workflow-pause-resume.md).

Технические повторы ограничены политикой узла. Действия, уже изменившие файлы или внешнее состояние, нельзя повторять вслепую. После аварийного завершения сессии восстановление явное: агент проверяет задачу, документы и фактические изменения. Автоматический второй исполнитель не запускается.

Отмена означает прекращение текущей работы, а не откат уже сделанных изменений. Запущенное действие должно завершиться или быть остановлено перед объявлением отмены.

## Хранение и ограничения v1

Текущий v1 не требует координации нескольких исполнителей. Возможное будущее расширение для нескольких сессий, индекса продолжений и восстановления описано в документе [«Координация нескольких запусков»](runtime-coordination.md); оно не является частью текущего API.

Контрольные точки между сессиями можно добавить позже в `.orchestrator/runs/`. В первом срезе нет обещания восстановить потерянное состояние памяти или автоматически возобновить процесс после перезапуска. История задачи в SQLite не является полной историей графа.

Существующий task-claim сохраняется как требование Task Manager для `ready → active`. Его lease не является блокировкой узлов графа; интеграционный адаптер должен соблюдать действующий API. Разработка нового многопользовательского планировщика не требуется.

## Будущие тесты

- Допустимый результат выбирает объявленный переход; неизвестный исход отклоняется.
- Во время вопроса пользователю следующий узел не выполняется.
- Ответ продолжает актуальное ожидание, не повторяя завершённые шаги без маршрута.
- Циклы и технические повторы ограничены политикой.
- Подготовка заканчивается на `ready` без автоматического исполнения в deferred-режиме.
- Успешный запуск исполнения не подменяет техническую проверку и приёмку задачи.
- После аварии отсутствует автоматическое повторное применение побочного эффекта.

Эти проверки будут добавлены при реализации; сейчас изменена только документация.
