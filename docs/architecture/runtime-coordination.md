# Будущая функция: координация нескольких запусков

**Статус:** будущая функция, не реализуется в текущем v1, 2026-09-15. Это отдельное направление развития для нескольких сессий, фоновых исполнителей и восстановления между сессиями. Оно не является частью текущего контракта [Workflow Run](workflow-run.md) и не должно использоваться при реализации v1.

Текущий v1 рассчитан на одного агента в реальном времени. Когда появится потребность в конкурирующих workers или автоматическом продолжении после потери сессии, этот документ станет исходной точкой отдельного этапа проектирования. Наличие описания не означает, что функция запланирована на ближайший релиз.

## Предлагаемая граница

Graph Runtime хранит свои снимки, события, намерения продолжения и активации в отдельной локальной SQLite-базе `.orchestrator/runs/runtime.sqlite3`. База Task Manager `.orchestrator/state/tasks.sqlite3` остаётся независимой. Runtime не читает и не меняет её напрямую.

Индекс продолжений — транзакционная проекция состояния runtime, а не третий источник истины. Снимок запуска, событие и изменение индекса фиксируются в одной транзакции runtime. Файлы рабочих артефактов в каталоге запуска не являются заменой этой транзакции.

Первый срез рассчитан на локальные процессы одного проекта и одного runtime-хранилища. Независимые checkout/worktree с разными базами, сетевые диски и несколько компьютеров не получают общей защиты от двойного исполнения. Для их поддержки нужно отдельно выбрать общий координатор; это не возможность v1.

## Продолжение

Запись содержит `task_ref`, `phase`, `run_id`, `wait_id`, версию контрольной точки, `continuation_id` и состояние намерения: `waiting`, `resume_requested`, `activating`, `consumed` или `recovery_required`.

Не более одного незакрытого продолжения на пару задача/фаза. Уникальность защищается хранилищем, а не предварительным поиском агента. Переходы выполняются с ожидаемой версией. Поглощение намерения фиксируется вместе с контрольной точкой успешной активации; история сохраняется.

Executor сначала разрешает маршрут задачи через runtime, затем получает task-claim и перед запуском повторно проверяет продолжение. Если другой worker выиграл claim, он продолжает тот же запуск. Создание нового запуска возможно только после транзакционной проверки отсутствия незавершённого продолжения. Недоступность индекса не означает пустой индекс: работа не стартует.

## Активация

Активация описывает право конкретного worker выполнять запуск: `activation_id`, `run_id`, `worker_ref`, возрастающее поколение `generation`, срок lease и состояние `reserved`, `active`, `stopped` или `recovery_required`.

Допустима одна незакрытая активация запуска и одна незакрытая активация задачи независимо от фазы. Для запусков до регистрации задачи уникальность задаётся по `run_id`; связывание с задачей должно проверить отсутствие её другой активации. Резервирование и проверки выполняются одной транзакцией runtime.

Рекомендуемый порядок исполнения:

1. Зарезервировать активацию в runtime без вызова узла.
2. Получить task-claim через публичный API; после конфликта не выполнять работу и согласовать резервирование с фактическим владельцем.
3. Проверить актуальный маршрут/продолжение и привязать запуск в Task Manager.
4. Зафиксировать активную активацию, task-claim и поглощение продолжения в runtime.
5. Только затем вызвать узел. Для подготовки task-claim отсутствует, но резервирование runtime обязательно.

Это уточняет [протокол паузы](workflow-pause-resume.md): право координации приобретается до попытки возобновления, однако право выполнять узел появляется только после всех проверок обоих владельцев состояния.

## Истечение lease и защита от старого worker

Результат принимается только от актуальных `activation_id`, `generation` и `attempt_id`. Старые результаты не двигают граф. Lease активации не заменяет task-claim; для исполнения должны быть действительны оба.

Истёкший lease переводит активацию к проверке восстановления, а не автоматически передаёт право второму worker. Поколение защищает запись результата, но не способно отменить уже запущенную запись файла или внешнюю операцию. Новая активация запрещена, пока остановка старого worker не подтверждена и неоднозначные эффекты не разрешены.

Адаптер исполнителя должен предоставлять проверку завершения/остановки. Если такой проверки нет, требуется явное восстановительное решение с подтверждаемыми свидетельствами. Отсутствие heartbeat само по себе не является свидетельством остановки.

## Межсервисные сбои

Нет общей транзакции между двумя SQLite-базами. Runtime сохраняет намерение операции до вызова Task Manager и результат согласования после него. При сбое перечитываются задача, её история и runtime. Нельзя повторить claim или изменение статуса только потому, что локальная запись результата отсутствует.

Резервирование, полученный claim или активная связь без завершённой активации требуют согласования. Нельзя запускать узел в таком промежуточном состоянии. Недостающий API перехода от устаревшего ожидания к подготовке остаётся отдельной задачей проектирования, не обходится этим индексом.

## Будущие проверки

- Два локальных процесса одновременно резервируют одну задачу или продолжение.
- Worker теряет lease и позднее присылает результат старого поколения.
- Сбой между резервированием, claim, привязкой и фиксацией активации.
- Истёкший lease при живом исполнителе запрещает новый запуск.
- Пустой, недоступный и противоречивый индекс различаются.
- Поглощение продолжения и контрольная точка фиксируются атомарно.
- Новый worker не начинает подготовленную задачу с начала после паузы.

Физическая схема таблиц, миграции, clock/heartbeat policy и публичный runtime API будут определены до реализации. Тесты выше пока не выполнены.
