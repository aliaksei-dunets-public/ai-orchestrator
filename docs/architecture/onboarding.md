# Первичная настройка целевого проекта

**Статус:** действующий контракт первого среза, 2026-09-14.

## Назначение и границы

Доставка ядра и настройка целевого проекта — разные операции. Внешний проект размещает ядро в `tools/graph-orchestrator/` как Git submodule или копию подготовленного пакета. Этот срез **не собирает и не копирует пакет**; он настраивает проект после размещения ядра. При self-hosting корень ядра и проекта совпадают, второй экземпляр не создаётся.

Агент отвечает за смысловые сведения о проекте. Он читает исходный код, инструкции и документы, затем готовит JSON с `project_name`, `summary`, `test_commands` и `constraints`. Не следует включать секреты или длинные сырые фрагменты исходников. Детерминированный модуль `graph_orchestrator.onboarding` отвечает за пути, формат файлов, проверку конфликтов и запись.

## Артефакты

| Путь в целевом проекте | Назначение и владелец |
| --- | --- |
| `.graph-orchestrator/project.json` | Версионируемая конфигурация проекта; создаётся инструментом. |
| `.graph-orchestrator/project-context.md` | Версионируемый смысловой контекст, подготовленный агентом; создаётся инструментом. |
| `AGENTS.md` | Во внешнем проекте только маркированный блок между `graph-orchestrator:begin/end`; остальное принадлежит проекту. При self-hosting существующий файл не меняется. |
| `.gitignore` | Только маркированное правило `.orchestrator/`, если эквивалентная строка ещё отсутствует. |
| `.orchestrator/` | Будущее рабочее состояние runtime; сейчас не создаётся и не переносится. |

Существующие `project.json` и `project-context.md` с другим содержимым блокируют повторную настройку. Это предохраняет пользовательские правки от перезаписи. Для их миграции понадобится отдельный контракт обновления.

## Протокол preview/apply

`preview` читает целевой проект и формирует план с точным содержимым изменяемых файлов, хешами их текущего и нового содержимого, абсолютными путями проекта и ядра, а также хешем всего плана. Запись файла плана выполняется только по явно указанному `--output`; целевые файлы не меняются. Показанный diff — основание для одного подтверждения пользователя.

`apply` получает файл плана и подтверждённый хеш. До первой записи он сверяет хеш плана, пути, набор разрешённых файлов, отсутствие символических ссылок и текущие хеши всех затрагиваемых файлов. Если что-то поменялось, применение останавливается без записи. После записи проверяются версия конфигурации, путь ядра и наличие контекста. При обычном сбое модуль восстанавливает прежнее содержимое уже изменённых файлов. Аварийное завершение процесса между несколькими заменами файлов пока не образует транзакцию; для такого случая нужен Git или внешняя резервная копия.

Проверка `preview` не заменяет пользовательское согласование. `apply` никогда не должен получать хеш, который пользователь не видел и не подтвердил.
