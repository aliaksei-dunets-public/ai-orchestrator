# Первичная настройка целевого проекта

**Статус:** действующий контракт первого среза, 2026-09-14.

## Назначение и границы

Доставка ядра и настройка целевого проекта — разные операции. Внешний проект размещает ядро в `tools/orchestrator/` как Git submodule или копию репозитория. Этот срез **не собирает и не копирует ядро**; он настраивает проект после его размещения. При self-hosting корень ядра и проекта совпадают, второй экземпляр не создаётся.

Агент отвечает за смысловые сведения о проекте. Он читает исходный код, инструкции и документы, затем готовит JSON с `project_name`, `summary`, `test_commands` и `constraints`. Не следует включать секреты или длинные сырые фрагменты исходников. Детерминированный пакет `orchestrator-onboarding` (`orchestrator_onboarding`) отвечает за пути, формат файлов, проверку конфликтов и запись. Он связан с принятой структурой ядра и не претендует на независимость Task Manager Service.

## Артефакты

| Путь в целевом проекте | Назначение и владелец |
| --- | --- |
| `.orchestrator/project.json` | Версионируемая конфигурация проекта; создаётся инструментом. |
| `.orchestrator/project-context.md` | Версионируемый смысловой контекст, подготовленный агентом; создаётся инструментом. |
| `AGENTS.md` | Во внешнем проекте только маркированный блок между `orchestrator:begin/end`, включая ссылки на onboarding и Task Manager skill внутри ядра; остальное принадлежит проекту. При self-hosting существующий файл не меняется. |
| `.gitignore` | Только маркированное правило `.orchestrator/state/`, если эквивалентная строка ещё отсутствует. |
| `.orchestrator/state/` | Локальное рабочее состояние Task Manager Service (SQLite); не версионируется. |

Существующие `project.json` и `project-context.md` с другим содержимым блокируют повторную настройку. Это предохраняет пользовательские правки от перезаписи. Для их миграции понадобится отдельный контракт обновления.

Онбординг не устанавливает Python-пакет Task Manager Service. После применения плана пользователь отдельно устанавливает его из `packages/task-manager/`, как описано в [инструкции](../guides/tasks.md). Skill-указатель размещён в `.agents/skills/` ядра, полный пример — внутри пакета Task Manager; внешнему агенту путь к указателю сообщает управляемый блок `AGENTS.md`.
При внешнем подключении preview проверяет наличие `orchestrator-task-manager` skill и MCP entry point `orchestrator-task-manager-mcp` в указанном ядре до создания ссылки на него в `AGENTS.md`. Порядок вопросов, preview/apply, отдельного подтверждения установки Task Manager и финальной проверки описан в [инструкции первого запуска](../guides/onboarding.md); сам пакет onboarding не выполняет установку молча.

После установки пакет onboarding предоставляет две явные проверки интеграции. `check-task-manager` запускает реальный MCP stdio handshake выбранным Python-интерпретатором и вызывает read-only `task_health_check`. `mcp-config` создаёт локальный host-neutral JSON-фрагмент с абсолютным интерпретатором и фиксированным корнем проекта. Ни одна команда не изменяет глобальную конфигурацию Codex или другого MCP-хоста.

Широкое правило `.orchestrator/` в существующем `.gitignore` блокирует preview: оно скрывает версионируемые конфигурацию и контекст. Перед настройкой пользователь должен отдельно согласовать замену такого правила на `.orchestrator/state/`.

## Протокол preview/apply

`preview` читает целевой проект и формирует план версии 2 с версией onboarding, отпечатком содержимого ядра, точным содержимым изменяемых файлов, хешами их текущего и нового содержимого, абсолютными путями проекта и ядра, а также хешем всего плана. Отпечаток ядра вычисляется по файлам ядра с исключением локальных каталогов `.git`, `.orchestrator`, `.tmp`, `.venv`, `build`, `dist` и `__pycache__`. Запись файла плана выполняется только по явно указанному `--output`; целевые файлы не меняются. Показанный diff — основание для одного подтверждения пользователя.

`apply` получает файл плана и подтверждённый хеш. До первой записи он сверяет версию формата и onboarding, хеш плана, пути, отпечаток ядра, набор разрешённых файлов, отсутствие символических ссылок и текущие хеши всех затрагиваемых файлов. Если что-то поменялось, применение останавливается без записи. После записи проверяются версия конфигурации, путь ядра и наличие контекста. При обычном сбое модуль восстанавливает прежнее содержимое уже изменённых файлов. Аварийное завершение процесса между несколькими заменами файлов пока не образует транзакцию; для такого случая нужен Git или внешняя резервная копия.

Для `AGENTS.md` используются HTML-комментарии `<!-- orchestrator:begin/end -->`, а для `.gitignore` — комментарии Git `# orchestrator:begin/end`, чтобы служебные маркеры не становились шаблонами игнорирования.

Проверка `preview` не заменяет пользовательское согласование. `apply` никогда не должен получать хеш, который пользователь не видел и не подтвердил.
