# Пауза и возобновление в сессии агента

**Статус:** упрощённый принцип подтверждён пользователем, 2026-09-15. Интеграция runtime ещё не реализована. Заменяет проект с индексом продолжений и исключительными активациями.

## Поведение графа

Один агент ведёт [запуск графа](workflow-run.md) в реальном времени. При необходимости ввода он сохраняет текущий шаг и вопрос в памяти, спрашивает пользователя и не выполняет следующий шаг.

После ответа тот же агент проверяет, относится ли он к текущему вопросу, добавляет его в данные ожидания и повторно выполняет текущий узел. Новый результат выбирает объявленный графом переход. Завершённые узлы не повторяются только из-за паузы. Для блокера сначала устраняется причина.

Текущий сценарий предполагает одну сессию агента. Поддержка нескольких сессий, автоматического продолжения и координации workers вынесена в отдельную [будущую функцию](runtime-coordination.md) и сейчас не реализуется.

## Граница с существующим Task Manager

Пауза графа и статус задачи — разные данные. Для зарегистрированной управляемой задачи адаптер фиксирует ожидание через публичный API и соблюдает уже существующие guards, а не меняет SQLite или правила сервиса.

Текущий API требует следующую последовательность для ожидания:

1. Прекратить выполнение шага. Перевести задачу в `awaiting_input` через `transition_status` или зарегистрировать блокирующий фактор через `add_blocker`.
2. Закрыть активную ссылку через `link_workflow_run(..., relation="finished")`.
3. Если есть task-claim исполнения, освободить его через `release_claim`, сохранив статус ожидания.
4. После ответа зарегистрировать решение через `record_user_decision`; для блокера — `resolve_blocker`. Проверку соответствия ответа вопросу выполняет агент/runtime: сервис проверяет лишь появление нового решения.
5. Вернуть задачу в её `resume_status` через `transition_status`: подготовка — `preparing`, исполнение — `ready`.
6. Для исполнения получить новый task-claim через `claim_task`, затем снова привязать тот же `run_id`. Для подготовки достаточно повторной привязки запуска.

Закрытие активной ссылки не означает терминальное завершение запуска графа. Он остаётся в памяти текущей сессии. Каждая мутация использует актуальную `expected_version`; конфликт требует перечитывания задачи, а не слепого повтора.

Это требования уже существующего Task Manager, не новая система блокировок графа. Claim продлевается по правилам сервиса во время исполнения; истёкший claim не даёт разрешения продолжать изменения без проверки.

## Изменение требований и завершение сессии

Если ответ меняет требования или документы устарели, нельзя продолжить прежний план. Возврат из ожидания исполнения прямо в подготовку текущим API не предусмотрен: `resume_status` указывает на `ready`, а guard может отказать. До согласования этого перехода агент сообщает об ограничении; не обновляет хеши фиктивно и не обходит guard.

После аварийного завершения память запуска может быть потеряна. Агент явно проверяет задачу, активные ссылки/claim, документы и фактические изменения, затем предлагает безопасное продолжение. Автоматическое восстановление или запуск второго исполнителя не входят в v1. Контрольные точки для новой сессии — отдельное будущее расширение.

## Будущие проверки

- Вопрос останавливает граф; ответ продолжает правильный шаг.
- Посторонний ответ не снимает текущее ожидание.
- Адаптер соблюдает порядок закрытия ссылки и освобождения task-claim.
- Устаревшие документы запрещают продолжение исполнения.
- Потеря сессии не вызывает автоматического повторного изменения проекта.

Функциональная проверка будет выполнена после реализации адаптера и runtime.
