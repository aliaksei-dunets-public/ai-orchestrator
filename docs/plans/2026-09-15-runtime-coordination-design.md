# Выбор хранения и координации runtime

**Статус:** будущая функция, не реализуется в v1, 2026-09-15. Исторический вариант возможной поддержки нескольких сессий; текущая архитектура зафиксирована в [решении для одного агента](2026-09-15-realtime-runtime-design.md).

## Варианты

1. Отдельная SQLite-база runtime со снимком, индексом и активацией в одной транзакции — рекомендуется для локального v1. Сохраняет независимость Task Manager, но межсервисные операции требуют восстановления.
2. Файловые снимки и lock-файлы — легче читать вручную, сложнее гарантировать атомарность снимка, истории и индекса; не рекомендуется как каноническая основа.
3. Общая база с Task Manager — уменьшает отдельные окна отказа, но связывает автономный пакет со схемой runtime; не рекомендуется.

Подробный [кандидат](../architecture/runtime-coordination.md) ограничивает гарантии одним локальным runtime-хранилищем. Он не вводит распределённое выполнение или автоматическое повторное исполнение после истечения lease.

После подтверждения: согласовать восстановительные переходы Task Manager, затем схемы артефактов и точный runtime API. До этого не писать движок графа.
