# Разделение Task Manager на модули

**Статус:** согласованный пользователем дизайн; TASK-0024, 2026-09-16.

## Решение

По итогам аудита пользователь разрешил разделить файл `task_manager.py` без изменения API и поведения. Рассмотрены сохранение монолита, разделение по ответственности и полная переработка моделей/переходов. Выбрано разделение по ответственности: оно упрощает проверку изменений и не требует новых зависимостей или схемы SQLite.

- `contracts.py`: ошибки, константы, базовая валидация, время и контекст событий.
- `migrations.py`: схема и транзакционный запуск миграций.
- `repository.py`: соединения SQLite, фильтры, атомарные записи snapshot/event/operation, tombstone.
- `service.py`: единый жизненный цикл и guards. Не дробить его на mixin-классы.
- `storage_transfer.py`: export/backup/restore, проверка копии и временные файлы.
- `diagnostics.py`: read-only проверки единого снимка SQLite с переданным ready-guard.
- `task_manager.py`: совместимые переэкспорты прежних классов и констант.

Сервис делегирует перенос состояния и диагностику композиционно. Репозиторий предоставляет явную внутреннюю границу `read_transaction`; SQL допустим в инфраструктурных модулях переноса и диагностики, но не в сервисе. Миграции имеют самостоятельный вход; restore не вызывает приватный метод репозитория. Файловые guards документов остаются рядом с жизненным циклом: их дополнительное выделение сейчас не требуется.

## Совместимость

Сохранить импорты `TaskManagerService`, `SQLiteTaskRepository`, `TaskError` из пакета и старого модуля, сигнатуры существующих публичных методов, JSON, коды ошибок и CLI. Схема остаётся версии 5. Приватные точки подмены в тестах переводятся в модули, где функция действительно исполняется; старые приватные helper-импорты могут остаться переэкспортами, но monkeypatch старого пути не является публичным контрактом.

Никаких фиктивных запусков или пользовательской приёмки. Учёт ведётся через API Task Manager; текущая Codex-сессия является реальным запуском подготовки и реализации.

## Проверка и порядок

1. Снять baseline и сохранить сигнатуры API до переноса.
2. Механически выделить модули, затем заменить приватные межмодульные вызовы явными границами.
3. Перенастроить предметные тесты и добавить проверки совместимости импортов, сигнатур, зависимостей и read-only транзакции.
4. Прогнать тесты пакета и потребителя, проверить wheel в изоляции без ядра.
5. Повторить одинаковые замеры на временных проектах; не обещать ускорение от разделения файлов.
6. Обновить архитектуру пакета, гайды, project-status и worklog. Подготовить результат к отдельной приёмке пользователя.

Существующие незакоммиченные изменения TASK-0023 сохраняются. `obsolete/`, `.venv/` и посторонние данные не изменяются. Дизайн хранится вместе с текущим рабочим деревом; отдельный коммит поверх незавершённого предыдущего среза не создаётся.
