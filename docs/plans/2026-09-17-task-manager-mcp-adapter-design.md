# Архитектура MCP-адаптера Task Manager

**Статус:** первый stdio-срез, интеграционное усиление onboarding/skill и полный аудит сценариев реализованы в TASK-0026; пользовательская приёмка задачи выполняется после финальной проверки.

## Решение

Создаётся один переиспользуемый пакет MCP-адаптера. Клиент запускает отдельный локальный stdio-процесс на каждый проект и передаёт ему фиксированный `project_root` при старте.

```text
Codex / MCP client
        │ stdio
        ▼
Task Manager MCP adapter (общий код, отдельный процесс)
        │ фиксированный project_root
        ▼
TaskManagerService
        │
        ▼
<project_root>/.orchestrator/state/tasks.sqlite3
```

Для двух проектов используется один и тот же пакет и две конфигурационные записи MCP. Это не две реализации сервера: разделены только процессы и базы. Общее мульти-проектное подключение одним процессом не входит в первый срез, потому что потребовало бы дополнительной маршрутизации, allowlist корней, контроля изоляции и тестов.

## Причины

Такой вариант сохраняет существующую модель владения состоянием: Task Manager отвечает за одну локальную базу проекта, а MCP остаётся транспортным слоем. Фиксированный корень уменьшает риск случайно выполнить мутацию в другом проекте. stdio не требует порта, внешнего HTTP-сервера или общего daemon-процесса. Один пакет позволяет исправлять и тестировать адаптер централизованно.

## Подключение

После установки пакета MCP-клиент получает команду запуска, рабочий каталог или аргумент `--project`, и при необходимости отдельное Python-окружение. Для каждого проекта добавляется запись с тем же command и своим `project_root`. Onboarding проверяет реальный handshake через `check-task-manager` и по явному вызову генерирует локальный host-neutral конфиг через `mcp-config`, используя выбранный абсолютный Python-интерпретатор. Глобальные настройки MCP-хоста автоматически не изменяются. CLI остаётся fallback для диагностики и ручной проверки.

## Границы адаптера

Адаптер не пишет SQLite напрямую, не содержит вторую копию guards и не создаёт собственное состояние. Он строго валидирует структурированные аргументы MCP по опубликованным схемам, вызывает публичные методы `TaskManagerService` и нормализует результаты/`TaskError`. Мутации передают `expected_version`; `operation_id` используется только там, где его поддерживает API. После конфликта версии адаптер не повторяет операцию сам. Результат `structuredContent` всегда объект: скалярные и списковые результаты находятся в `value`, ошибки — в `error`.

В первый срез не входят HTTP daemon, кэш, пакетные мутации, изменение схемы, внешний Task Tracker и Graph Runtime. Файловые аргументы MCP также ограничены фиксированным project root. Onboarding не регистрирует MCP в конкретном GUI-хосте: формат и область глобальной конфигурации зависят от хоста, поэтому пакет выдаёт только проверяемый локальный фрагмент.

## Реализованный первый срез

Пакет предоставляет `orchestrator-task-manager-mcp` и модуль `task_mcp.py`. Реализованы строгий MCP lifecycle, согласование поддерживаемых версий, `tools/list`, `tools/call`, schema validation, 35 инструментов поверх публичного сервиса, объектный формат структурированных результатов и `TaskError`, фиксированный project root, ограничение файловых путей и защита stdio stdout от постороннего вывода. Внешних зависимостей не добавлено.

## Проверки

Проверено subprocess-клиентом: полный lifecycle от создания до архивации, ошибки и guard, конфликт версии, изоляция нескольких project root, Unicode, restart и отказ путей за root. Benchmark `benchmark_task_mcp.py --count 100` дал фактический startup initialize 124.702 ms, тёплый `task_get` p50 0.350 ms и p95 0.551 ms на текущем окружении. Реальный onboarding handshake и локальный конфиг проверяются отдельными тестами; проверка конкретного GUI-хоста и пользовательская приёмка остаются отдельным шагом.
