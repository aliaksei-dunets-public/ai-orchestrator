# Core Repository State Boundary Implementation Plan

> **For agentic workers:** Implement this plan task-by-task using the repository's approved execution workflow.

**Goal:** Ensure the core repository contains no tracked `.orchestrator` project state or machine-specific development paths while every target project still receives a fresh, functional orchestration state through onboarding.

**Architecture:** Treat `.orchestrator` as target-project-owned state, never as core source. The core repository ignores and untracks its own local state, while release artifacts continue to contain only portable core directories. Target onboarding keeps its explicit, selective target `.gitignore` policy for canonical project memory and Knowledge Graph stores.

**Tech Stack:** Git, Python 3.11+, standard-library runtime, JSON/YAML configuration, Markdown documentation, `unittest`, release artifact builder, onboarding workflow, and repository audit.

## Global Constraints

- Do not rewrite existing Git history in this task; stop tracking the core repository's `.orchestrator` state from the new boundary onward.
- Preserve target-project onboarding behavior and its selective ignore policy for canonical target memory and Knowledge Graph stores.
- Preserve release portability: release artifacts must not contain `.orchestrator` state from the core repository.
- Do not commit registry files, checkpoints, receipts, temporary files, locks, release artifacts, or other generated operational state.
- Remove absolute machine-specific paths from canonical core documentation without changing historical Russian baseline meaning.
- Keep runtime platform-neutral and preserve immutable security policies.

## Deliverables

- Core `.gitignore` and documentation/specification boundary that declares `.orchestrator` target-owned and non-portable.
- Removal of currently tracked core `.orchestrator` files from the Git index with a recoverable local migration path.
- Portable canonical documentation without `C:\\Users\\...\\ai-orchestrator` or equivalent machine-specific paths.
- Contract and acceptance tests for core state exclusion, release isolation, onboarding freshness, and machine-path rejection.
- Validation evidence from full tests, strict Health Check, language inventory, and repository audit.

## Dependencies

- Existing release artifact behavior in `orchestrator/release.py`.
- Existing target onboarding behavior in `orchestrator/onboarding_workflow.py`.
- Current core `.gitignore`, task-layer specification, orchestrator specification, documentation map, and release/onboarding test suites.
- User-approved approach: core repository state is not portable and target projects initialize their own state.

## Acceptance Criteria

- `git ls-files .orchestrator` returns no core repository state paths after migration.
- The core repository `.gitignore` excludes `.orchestrator/` without changing the target-project ignore manifest generated by onboarding.
- A release artifact contains no `.orchestrator` paths and installs core without importing the source repository's state.
- Fresh target onboarding creates the target-owned `.orchestrator` structure and retains canonical target memory/Knowledge Graph paths according to its existing policy.
- Canonical core files contain no absolute path rooted in a developer workstation and no reference to the core repository's local state directory.
- Full discovery, affected acceptance/contract tests, strict Health Check, language inventory, and repository audit pass.
- No existing Git history is rewritten and no user data outside the repository is deleted.

## Testing Strategy

- Contract tests inspect the core `.gitignore`, canonical path scan, and release artifact file set.
- Onboarding scenario tests verify a fresh target state and the unchanged selective target ignore manifest.
- Release acceptance tests verify clean installation and absence of source `.orchestrator` state.
- Full unittest discovery, strict Health Check, language inventory, local Markdown links, and read-only repository audit provide final evidence.

## Risks and Rollback

- **Risk:** Removing tracked state could hide useful core-development history. **Detection:** pre-migration manifest and digest are recorded. **Rollback:** restore the local state snapshot and re-add only through an explicitly approved follow-up; do not rewrite Git history.
- **Risk:** Broad core ignore rules could leak into target onboarding output. **Detection:** onboarding contract tests compare the generated target `.gitignore` and canonical-store rules. **Rollback:** restore the owned onboarding ignore block and revert the core-only rule.
- **Risk:** Documentation cleanup could alter historical baseline content. **Detection:** compare canonical English documents with their Russian baseline metadata and run link/inventory checks. **Rollback:** restore only the affected canonical wrapper lines.
