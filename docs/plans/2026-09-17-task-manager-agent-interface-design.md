# Исправление CLI и выбор интерфейса агента

**Статус:** исправление CLI разрешено пользователем и реализуется в TASK-0025. Выбор нового адаптера — рекомендация для согласования, не реализованная функция.

## Подтверждённая проблема

[Независимый аудит Luna](../reports/2026-09-17-task-manager-agent-audit-luna.md) обнаружил одну ошибку: CLI export вызывает отсутствующий метод export вместо export_state. Исправление ограничено общим реестром команд переноса для parser/dispatch. Не меняются публичный API, схема, guards и зависимости. Нужны реальные subprocess-проверки успешного экспорта и JSON-ошибок, неизменность карточек/истории и backup/restore на временной базе.

## Варианты взаимодействия

| Вариант | Применение | Ограничение |
| --- | --- | --- |
| CLI + skill | Работает сейчас, универсальный резервный путь | Новый Python-процесс на команду, shell-экранирование, подробные ответы |
| Встроенные инструменты → Python API | Предпочтительный путь внутри Python-оркестратора | Нужен инструментальный host в процессе агента; сам LLM не вызывает Python напрямую |
| Локальные MCP-инструменты через stdio → Python API | Рекомендуемый следующий интерфейс для внешнего агента Codex | Отдельный небольшой пакет/транспорт, проверка интеграции и согласование перед реализацией |

Общий принцип: агент вызывает структурированный инструмент, адаптер валидирует аргументы, вызывает публичный TaskManagerService и возвращает структурированный результат или TaskError. Адаптер не содержит SQL, собственной базы, копии guards или отдельного состояния процесса Graph Runtime. Это не отложенный Task Tracker Adapter для внешнего трекера TASK-0018.

Для Codex предпочтителен локальный MCP stdio, а не новый HTTP-сервер: инструментальный процесс может обслуживать много вызовов без отдельного запуска CLI на каждый. В Python-оркестраторе та же инструментальная граница регистрируется непосредственно, без лишнего транспорта. Долгоживущий процесс не требует долгоживущего SQLite-соединения: сохраняется текущий транзакционный жизненный цикл репозитория. Управление запуском/остановкой адаптера принадлежит клиенту; restore допускается только при координированной остановке других клиентов и мутаций.

## Безопасность и объём следующего среза

В [официальном описании stdio](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/transports/stdio.mdx) клиент запускает MCP-процесс и обменивается сообщениями через стандартные потоки. Это подтверждает модель транспорта, но не готовность нашего адаптера.

- Корень проекта задаётся при подключении; не выбирается произвольно в каждой мутации. Реестр инструментов явно сопоставляется публичным методам, схемы и параметры проверяются контрактными тестами.
- expected_version явно передаётся в мутациях. operation_id доступен только поддерживающим его методам; сохраняются первоначальные параметры повтора. Конфликт версии не повторяется автоматически. Для остальных методов после неопределённого результата сначала проверяются карточка и история.
- Чтение использует summary и cursor-пагинацию; возможная компактная проекция требует отдельного контракта. Сейчас list возвращает полные карточки, table предназначен человеку.
- Приёмка, purge и restore не превращаются в обычные автоматические действия. Разрешение исполнить задачу не считается приёмкой её результата.
- На старте не нужны кэш карточек, пакетные мутации, сетевой daemon или изменения хранилища. CLI остаётся резервным путём.

## Основание выбора и будущие проверки

В аудите одной карточки средний тёплый get_task в существующем Python-процессе составил около 0,25 мс; отдельный CLI show — около 149 мс. CLI-замер включает запуск процесса, parser и создание сервиса; API-замер не включает создание сервиса. Это аргумент убрать повторные запуски, а не измерение MCP и не обещание ускорения всего агента в 600 раз.

Перед реализацией адаптера нужно согласовать этот отдельный срез. Затем проверить объявление и вызов инструментов реальным клиентом, весь lifecycle на временном проекте, обработку ошибок/конфликтов/неопределённого результата, Unicode/пути, остановку/перезапуск процесса и задержки p50/p95. До этих проверок нельзя объявлять адаптер готовым или более стабильным, чем текущий CLI.
