# Дизайн Artifact Repository v1

**Статус:** согласованный дизайн реализации TASK-0014, 2026-09-17.

## Рекомендуемый вариант

Для первого среза используется локальный filesystem repository поверх стандартной библиотеки Python. Это минимально сложный вариант для текущего локального Orchestrator: артефакты доступны без второй базы, хранятся рядом с проектом и могут быть проверены по SHA-256. SQLite Task Manager и in-memory Graph Runtime остаются независимыми владельцами своего состояния.

Альтернатива с записью артефактов в SQLite отклоняется: она смешала бы payload и lifecycle задач, увеличила бы транзакционную поверхность и нарушила установленную границу хранения. Внешнее object storage откладывается: оно потребует credentials, сетевую семантику, отдельный адаптер и политики повторов, которые не нужны для v1.

## Структура хранения

```text
.orchestrator/artifacts/
└── <ref>/
    └── <role>/
        └── <version>/
            ├── manifest.json
            └── payload.bin
```

`ref`, `role` и `version` принимаются только как безопасные одноуровневые идентификаторы без `/`, `\\`, `..`, control characters и абсолютных путей. Уникальным ключом публикации является тройка `ref + role + version`; это позволяет одному `ref` иметь независимые plan/review/result-роли. Все три сегмента записываются в манифест и путь строится только из проверенных значений. Манифест содержит `format_version`, `ref`, `role`, `version`, `contract`, `media_type`, `sha256`, `size` и фиксированное имя payload.

## API и целостность

`ArtifactRepository.put(ref, role, version, ...)` принимает bytes или UTF-8 text; `put_json` сериализует JSON канонически (`sort_keys=True`, UTF-8, без ASCII-экранирования). Возвращается immutable `ArtifactRecord`. `get(ref, role, version)` возвращает record и bytes, `list` — только метаданные, `verify(ref, role, version)` повторно читает payload и проверяет размер/хеш.

Оба файла сначала полностью записываются во временный каталог `.staging-*`, проходят flush/fsync и только затем публикуются единым `os.rename` каталога версии. При обычном отказе staging очищается; при аварийной потере процесса оставшийся staging не считается опубликованной версией и не ломает `list`. Если версия уже существует, идентичные тело и метаданные возвращаются идемпотентно, а отличающиеся отклоняются `artifact_exists`; опубликованные файлы не перезаписываются. Повреждённый payload/manifest возвращает `integrity_error`, отказ доступа/ввода-вывода — `repository_failure`.

На всех платформах запрещены Windows reserved names и trailing dot; регистр сохраняется, но alias существующего сегмента, отличающийся только регистром, отклоняется. Любой symlink/junction/reparse-компонент от `project_root` до читаемого или записываемого файла запрещён, включая сам repository root. Гарантия относится к обычному использованию одним процессом; защиты от конкурентного злоумышленника, меняющего файловую систему между проверкой и доступом, и подтверждения сохранности при отказе питания v1 не обещает.

## Ошибки и тестирование

`ArtifactError` содержит `code`, сообщение и details: `validation_failed`, `artifact_not_found`, `artifact_exists`, `integrity_error`, `repository_failure`. Тесты проверяют traversal, абсолютные пути, разные версии, роли, canonical JSON, повторную запись, ручное изменение payload/manifest, отсутствие артефакта и изоляцию корня проекта. Репозиторий не импортирует `orchestrator_task_manager` и `sqlite3`.
