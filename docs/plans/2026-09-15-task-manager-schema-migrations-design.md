# Дизайн: миграции схемы Task Manager

**Статус:** утверждён для реализации в `TASK-0005`.

## Контекст

Task Manager хранит текущую версию схемы в `PRAGMA user_version`. Сейчас схема создаётся непосредственно в конструкторе репозитория, а будущие изменения потребовали бы ручного редактирования существующих баз.

## Варианты

1. **Встроенный реестр миграций** — каждая версия имеет функцию перехода, репозиторий применяет их последовательно внутри транзакции. Это выбранный вариант: минимальное изменение, нет новой зависимости и сохраняется граница Task Manager.
2. Отдельный пакет миграций — лучше для нескольких сервисов, но сейчас создаёт лишний слой и не нужен локальному SQLite-инструменту.
3. Полное восстановление snapshot из событий — не подходит: события являются аудитом, а не текущей моделью event-sourcing.

## Решение

- Ввести константу текущей версии схемы и реестр переходов `0 → 1`.
- Вынести создание таблиц `meta`, `tasks`, `events` и индекса в миграцию базовой схемы.
- Открытие базы с версией `0` применяет миграцию до текущей версии.
- Открытие базы с текущей версией оставляет данные без изменений.
- Версия выше поддерживаемой отклоняется до записи данных.
- Миграции выполняются последовательно в `BEGIN IMMEDIATE`; при ошибке транзакция откатывается.

Публичный API задач, событий и lifecycle не меняется. Graph Runtime, отдельная runtime-база и блокировки в эту работу не входят.

## Проверки

- свежая база создаёт текущую схему;
- существующая база версии 1 сохраняет задачи и события;
- будущая версия отклоняется с `TaskError(repository_failure)`;
- пакетные и корневые тесты проходят.
