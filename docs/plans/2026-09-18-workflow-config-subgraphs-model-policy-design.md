# Конфигурация workflow, переиспользуемые подграфы и модели узлов

**Статус:** история архитектурного предложения и согласования от 2026-09-18. Пользователь разрешил реализацию; TASK-0036 реализует первый срез конструктора, TASK-0037 хранит интеграцию исполнения. Действующий формат находится в [контракте](../architecture/workflow-builder.md) и [guide](../guides/workflow-builder.md). Эскизы ниже не являются поддерживаемым TOML; сведения об отсутствии реализации отражают снимок до TASK-0036.

## Основания и фактическое состояние

Вопрос уже проработан в исходных материалах:

- [Правила переиспользуемых подграфов](../development/07-reusable-subgraph-design-rules.md): стабильные контракты, явные эффекты, независимость от модели и проекта, версионирование; дальнейшим маршрутом владеет вызывающий workflow.
- [Настройка Context](../development/03-context-node-knowledge-map-configuration.md), раздел 7: приоритет `Node → Workflow → Project Profile → Core default`.
- [Модельная политика](../graph/01-request-routing-and-task-architecture.md), раздел 10: логические профили `cheap`, `standard`, `expert`; конкретные модели задаются окружением или проектом, а не skill.
- [Testing](../development/22-testing-subgraph-architecture.md) и [его контракт](../development/23-testing-contract.md): детерминированный запуск тестов через capabilities проекта, модель для анализа области и причин отказов.
- [Documentation](../development/25-documentation-subgraph-architecture.md), [его контракт](../development/26-documentation-contract.md) и [политика](../development/27-documentation-policy.md): проверка влияния, выбор целей, обновление и валидация; `no_change` является нормальным результатом.

Это архитектурные правила и кандидаты контрактов, а не готовый механизм загрузки. По [актуальному статусу](../project-status.md) и исходникам `Node` содержит контракты, outcomes, transitions и требования outputs; `Graph.from_dict` строит плоский граф. Подготовка и execution gates собираются программно. Профилей модели, библиотеки компонентов и проектной композиции в этом API нет. `.orchestrator/project.json` хранит настройки подключения проекта и не является конфигом workflow.

## Выбор подхода

| Подход | Преимущества | Ограничения |
| --- | --- | --- |
| Копировать графы в каждый проект | Простое начало | Исправления расходятся, переиспользование и обновления становятся ручными |
| Библиотека компонентов, проектные overrides, компиляция в плоский Graph | Сохраняет текущий runtime; позволяет проверять композицию до запуска | Нужны компилятор, реестр контрактов и адаптация фасадов |
| Отдельные вложенные process runs | Самостоятельные жизненные циклы подграфов | Усложняет waits, бюджеты, синхронизацию и восстановление; предлагается отложить |

Рекомендуется второй вариант. Компиляция разворачивает декларацию в граф допустимых действий; смысловое исполнение остаётся у агента, самостоятельный Python reasoning loop не вводится.

## Библиотека компонентов

Компонент — атомарный узел или подграф с manifest: `id`, версия, входной и выходной контракт, именованные outcomes, entry, соответствие внутренних выходов публичным outcomes, допустимые параметры и явные эффекты. Версии компонента и контракта результата независимы. Ссылки разрешаются в точную версию и digest; нефиксируемая ссылка `latest` для запуска не допускается.

Workflow подключает, например, `core/testing@1` и `core/documentation@1`. Testing возвращает результат тестирования; вызывающий workflow решает, перейти ли к документации, исправлению реализации или блокировке. Подграф не ссылается на узлы конкретного родителя.

Каждый экземпляр получает пространство имён: `testing.run_checks`, `testing.classify_failures`. Два экземпляра одного компонента независимы. Сопоставление внутренних ID, экземпляра и логической роли сохраняется для истории, overrides и наблюдаемости. Компилятор проверяет контракт входов, привязки артефактов, все выходные порты и переходы. Выход подграфа оформляется явно; внутренний `succeeded` не должен случайно завершать весь процесс.

Ожидание остаётся ожиданием текущего внутреннего узла по действующему AgentGraphRuntime. Лимиты назначаются внутренним узлам и всему run; отдельный агрегированный бюджет компонента потребует нового механизма и не заявляется существующим.

Переиспользование имеет смысл для самостоятельного процесса со стабильным результатом. Testing и Documentation подходят; каждый небольшой узел превращать в подграф не требуется.

## Модель и способ исполнения

У узла отдельно описываются:

- структурный контракт: входы, выходы, outcomes, transitions;
- параметры компонента: область тестов, стратегия документации, повторы и прочее;
- `execution`: вид исполнителя, `model_profile`, необходимые возможности и разрешённая политика fallback/escalation.

Профиль связывает логическое имя с провайдером/хостом, конкретной моделью и поддерживаемыми параметрами рассуждения. Секреты не хранятся в workflow. У составного компонента профиль может задавать default для агентских внутренних узлов; детерминированный запуск тестов не превращается в вызов LLM из-за этого default.

Адаптер хоста проверяет доступность выбранной модели и фактически выполняет поручение. Текущий агент может выполнить узел сам только при соответствии разрешённой политике. Другая модель требует поддерживаемого хостом переключения или явно допустимого делегирования. Single-agent политика не должна автоматически заменяться запуском множества sub-agents.

Недоступная модель даёт явный отказ подготовки/blocked, если нет разрешённого fallback. Само поле `model_profile` не доказывает, что результат выполнен этой моделью: нужны сведения адаптера о фактическом исполнителе и использованном профиле. Автоматическая эскалация по оценке качества остаётся отдельной будущей возможностью.

## Переопределения целевого проекта

Предлагается отдельный `.orchestrator/workflow.toml`; существующий `project.json` сохраняет свою роль. Конфигурация выбирает библиотечный workflow, связывает модели и capabilities проекта, затем явно изменяет экземпляры компонентов.

Нужно различать два правила приоритета:

1. Источники определения: библиотека → определение workflow → проектный overlay. Overlay может изменить даже явно заданный атрибут узла.
2. После применения overlay недостающая политика наследуется по специфичности: узел → workflow → Project Profile → core default. Это сохраняет исходное решение Context; project default не перебивает явное значение узла.

Операции:

- `patch`: изменяет перечисленные поля известного экземпляра; словари объединяются по ключам, скаляры и списки заменяются целиком. Неизвестные поля и ID отклоняются. Пустое значение имеет смысл только по схеме; `[]` не означает удаление узла.
- `replace`: заменяет реализацию узла/подграфа ссылкой на зарегистрированный компонент. Параметры прежней реализации не наследуются молча. Внешние связи экземпляра сохраняются только при совместимых контрактах и выходных портах.

Несовместимая замена требует новой версии контракта и явного изменения вызывающего workflow. Проверка совместимости должна учитывать структуру артефактов и смысл обязательных результатов, а не только одинаковые строки имён контрактов. Overrides внутреннего узла адресуются через экземпляр и проверяются до разворачивания графа. Конфиг не содержит исполняемые выражения или произвольные Python imports.

Иллюстрация проектного overlay; это предложенный синтаксис, сейчас он не загружается ядром. Имена моделей ниже — заполнители. Предполагается, что библиотека и проект зарегистрировали указанные компоненты.

```toml
schema_version = 1

[workflow]
extends = "core/development@1"

[model_profiles.standard]
provider = "host"
model = "PROJECT_STANDARD_MODEL"

[model_profiles.expert]
provider = "host"
model = "PROJECT_EXPERT_MODEL"

[nodes.testing]
operation = "patch"

[nodes.testing.config]
max_transient_retries = 1

[nodes.testing.execution]
model_profile = "standard"

[nodes.documentation]
operation = "replace"
ref = "project/domain-documentation@1"

[nodes.documentation.execution]
model_profile = "expert"
```

Этот пример изменяет параметры Testing и заменяет Documentation компонентом целевого проекта; структура общего workflow сохраняется при совместимости внешних интерфейсов. Обязательные review, ready/preflight/claim и явная приёмка остаются ограничениями фасадов; замена компонента не позволяет их обойти.

## Уточнение: агентская сборка и интерактивный просмотр

Пользователь подтвердил ручную композицию блоков, но предпочёл основным интерфейсом skill для совместного проектирования процесса с агентом. Редактирование TOML остаётся доступным; визуальный редактор с перетаскиванием не требуется для первого среза.

Предлагается проектный skill `orchestrator-workflow-builder`. Его область — проектирование и изменение определений узлов, подграфов и workflow; построение определения само по себе не запускает процесс и не меняет состояние задачи. В беседе агент уточняет цель, входы, ожидаемые артефакты, маршруты, повторы, ожидания и условия завершения. Затем выбирает существующие блоки из каталога; при необходимости создаёт новый блок с инструкцией/skill, контрактами и descriptor исполнителя. Композиция из готовых блоков и создание нового блока являются разными действиями с разными результатами проверки.

Skill обращается к поддерживаемым схемам и публичным интерфейсам tooling. Повторяемая механика — разрешение ссылок, проверка контрактов, компиляция и генерация представления — выполняется детерминированными инструментами, а не заново придуманными агентом проверками. Если compiler или validator ещё отсутствуют, результат обозначается как проект определения, а не готовый к исполнению workflow.

Skill сопровождают каталог manifest компонентов, ссылки на контракты и несколько предметных примеров. Инструкция skill не становится новым хранилищем всех контрактов; реализации узлов и инструкции агентов остаются в соответствующих блоках библиотеки.

Для просмотра предлагается самостоятельный локальный HTML-файл, открываемый в браузере без сервера и сетевых зависимостей. Он генерируется из структурированного представления того же определения, которое проверяется перед запуском. Первая версия позволяет:

- выбирать узел и читать карточку: назначение, входы/выходы, инструкция или skill, модельный профиль, capabilities, эффекты и лимиты;
- раскрывать подграфы и возвращаться к родителю через навигационную цепочку;
- выбирать переход и видеть outcome, передаваемые артефакты и целевой узел;
- искать по ID/названию, перемещать схему и изменять масштаб;
- видеть ошибки определения и происхождение эффективных настроек: библиотека, workflow, проектный override;
- переходить к TOML-фрагменту или позиции исходного определения в карточке.

До реализации model bindings карточка показывает заданный профиль, а не выдуманную фактически использованную модель. Просмотр определения не изображает реальные runtime статусы. Позднее отдельный экспорт истории run сможет добавить фактический маршрут и evidence; HTML без подключения к runtime остаётся снимком.

Канонический источник — TOML и библиотечные manifests; промежуточное JSON-представление и HTML являются производными. Схема не рисуется агентом независимо от определения. Для вложенности renderer получает дерево компонентов, а не только развёрнутый плоский Graph; у исходных блоков и runtime узлов сохраняется явное соответствие ID. Группировка по имени с точкой сама по себе не заменяет такое дерево.

Пользовательский цикл: обсуждение процесса → создание/изменение определения → проверка → генерация HTML → просмотр конкретных узлов → уточнение в беседе → повторная генерация. Первый viewer служит инспектором. Редактирование графа в браузере с экспортом изменений можно добавить позже поверх того же формата.

Возможные варианты: встроенная схема в разговоре подходит для быстрых объяснений; отдельный HTML-инспектор рекомендуется для сохраняемого результата; приложение с сервером оправдано позже при live runtime и совместном редактировании. Skill и самостоятельный инспектор не требуют реализации такого приложения на первом этапе.

Выход работы skill: определение процесса, новые или изменённые блоки при необходимости, результат доступных проверок и связанный HTML-инспектор с указанием версии/digest определения. Первый вертикальный срез предлагается проверить на небольшом Testing-подграфе с развилкой результатов; исполнение произвольной композиции в текущих фасадах остаётся отдельной интеграционной работой.

## Загрузка, фиксация и интеграция

Загрузчик должен возвращать пакет `ResolvedWorkflow`: плоский `Graph`, параметры runtime, descriptors исполнителей, bindings профилей/capabilities, точные версии компонентов, digest и происхождение эффективных значений. Названия API предварительные. Одного `Graph.from_config(path)` недостаточно: текущий Graph не хранит эти сведения.

Уточнение предыдущего эскиза: требования выходов по outcome следует записывать как `required_outputs_by_outcome`; существующий `required_outputs` — список общих обязательных ключей, а не словарь исходов.

Разрешённая конфигурация фиксируется до подготовки и связывается с Plan/Review/Execution Package. Изменения файла во время run не меняют уже выбранную политику. Execution preflight проверяет привязку workflow snapshot вместе с существующими привязками задачи и source revision; digest конфигурации нельзя выдавать за code-corpus revision. Механизм изменения политики активного run в первый срез не включается.

Существующие AgentPreparation/AgentExecution имеют фиксированные этапы и обработчики результатов. Загрузчик TOML сам по себе не сделает их заменяемыми. Нужны логические роли компонентов и зарегистрированные обработчики результатов с прежними publication/sync/ready/claim guards. Для подграфов также необходимы явные передачи контекста и артефактов; разворачивание стрелок этого не решает.

## Предлагаемая последовательность

1. Схема TOML и resolver: действующие графы как библиотечные определения, строгая валидация, bindings профилей и project `patch`, фиксированный snapshot с объяснением происхождения значений.
2. Host-neutral execution descriptors и адаптеры: проверяемая доступность/выбор модели без изменения детерминированного runtime и политики single-agent.
3. Реестр компонентов, роли/обработчики фасадов и композиция подграфов с входами/выходами, артефактами и namespace. Первый вертикальный пример — Testing, затем Documentation.
4. Совместимая проектная замена атомарного узла и подграфа, проверки stale snapshot, негативные проверки обхода фазовых guards и пользовательский guide.

Эта последовательность — предложение к включению в текущий roadmap, а не новая утверждённая очередь задач. Изменения runtime, поставки и adapters следует согласовать с существующими этапами; Task Manager и его SQLite не менять.

## Проверки документа

Иллюстрация TOML проверена стандартным `tomllib` только на синтаксис. Локальные ссылки проверены; `git diff --check` выполнен. Работоспособность предложенного resolver, компонентов и model dispatch не заявляется. Код и состояние задач этим разбором не изменяются.
